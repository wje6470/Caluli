## User Scenarios & Testing *(mandatory)*

### User Story 1 - 從 LINE 入口登入並取得每日熱量目標 (Priority: P1)

使用者從 LINE 好友或官方帳號選單點擊入口進入服務（或直接以一般瀏覽器開啟網頁版），系統辨認目前的執行環境並完成 LINE 身分驗證：在 LINE 內開啟時使用者無需額外操作即完成登入；在一般瀏覽器開啟時，使用者主動點擊「使用 LINE 登入」完成授權。首次使用者接著依序填寫性別、年齡、身高、體重與日常活動量，系統計算並呈現每日建議熱量（TDEE）與三大營養素目標，使用者確認後進入主儀表板。已完成建檔的使用者再次進入時直接抵達主儀表板。

**Why this priority**: 身分與每日熱量目標是其他所有功能的前提——沒有登入就沒有可歸屬的紀錄，沒有目標值儀表板與趨勢圖都失去比較基準。這也是唯一橫跨兩種執行環境的流程，最早驗證可及早暴露環境判斷缺陷。

**Independent Test**: 可獨立驗證——在 LINE 內與一般瀏覽器各走一次「進入 → 登入 → 填寫個人資訊 → 看到每日建議熱量」，即使尚未有任何拍照功能，使用者也已獲得「我每天該吃多少」的價值。

**Acceptance Scenarios**:

1. **Given** 使用者在 LINE App 內點擊官方帳號選單的服務入口，**When** 頁面開啟，**Then** 系統判定為 LINE 內執行環境並自動完成身分驗證，使用者無需手動輸入任何帳號資訊。
2. **Given** 使用者以一般手機或桌機瀏覽器開啟服務網址，**When** 頁面開啟，**Then** 系統判定為非 LINE 內執行環境，顯示「使用 LINE 登入」按鈕，使用者點擊後導向 LINE 授權頁，授權完成後回到服務並處於已登入狀態。
3. **Given** 使用者為首次登入且尚無個人健康檔案，**When** 登入完成，**Then** 系統導向個人資訊填寫流程，且在完成前不允許進入主儀表板。
4. **Given** 使用者已填入性別、年齡、身高、體重與活動量，**When** 送出，**Then** 系統顯示每日建議總熱量與蛋白質／碳水／脂肪目標值，並在使用者確認後進入主儀表板。
5. **Given** 使用者已有個人健康檔案，**When** 再次由任一入口進入，**Then** 系統直接顯示主儀表板，不重複要求填寫個人資訊。
6. **Given** 使用者在一般瀏覽器拒絕 LINE 授權或中途取消，**When** 回到服務頁面，**Then** 系統顯示未登入狀態與可再次嘗試登入的操作，不出現錯誤畫面或空白頁。

### User Story 2 - 拍照辨識、調整份量並儲存一筆飲食紀錄 (Priority: P2)

使用者在主儀表板點擊「拍照記帳」，選擇「使用相機即時拍照」或「從手機相簿上傳」提供餐點照片。系統送出辨識並顯示進行中狀態；辨識完成後，畫面列出照片中偵測到的每一項食物，每項顯示辨識出的食物名稱、系統套用的預設份量（公克）以及依該份量換算的熱量與三大營養素。使用者可逐項調整份量，畫面上的熱量與營養素隨調整即時重新計算；也可修正食物名稱、移除誤判的品項。確認無誤後儲存，系統寫入當日紀錄並返回儀表板，今日已攝取與剩餘熱量即時更新。

**Why this priority**: 這是產品的核心價值主張——「拍一張照片就掌握攝取熱量」。其中「預設份量 + 可即時調整」是本產品在模型無法估算克數前提下的關鍵補償設計，屬核心互動而非次要細節。

**Independent Test**: 可獨立驗證——以一張含食物的照片走完「上傳 → 等待 → 看到辨識結果 → 拖動份量看到數值變動 → 儲存 → 儀表板數字增加」，即完整交付一次記帳價值。

**Acceptance Scenarios**:

1. **Given** 使用者在儀表板點擊「拍照記帳」，**When** 選擇上傳方式，**Then** 系統提供「相機拍照」與「相簿選取」兩種來源，兩者最終進入同一套辨識流程。
2. **Given** 照片已送出辨識，**When** 系統尚未回覆結果，**Then** 畫面持續顯示明確的「分析中」狀態，且使用者無法重複送出同一次辨識請求。
3. **Given** 辨識回傳兩項以上食物，**When** 結果畫面呈現，**Then** 每一項食物各自獨立顯示名稱、份量（公克）、熱量與蛋白質／碳水／脂肪，並各自可調整。
4. **Given** 某項食物的預設份量為 250 公克且畫面顯示對應熱量，**When** 使用者將份量調整為 375 公克，**Then** 該項的熱量與三大營養素立即依「每 100 公克數值 × (調整後公克數 ÷ 100)」重新計算並更新顯示，使用者無需按下任何「重新計算」按鈕。
5. **Given** 使用者調整了任一項的份量，**When** 畫面更新，**Then** 本次紀錄的合計熱量與營養素同步更新。
6. **Given** 辨識出的食物名稱有誤，**When** 使用者從系統提供的其他候選名稱中改選，**Then** 系統改以新食物的每 100 公克營養值與預設份量重新換算並更新畫面。
7. **Given** 辨識結果中有一項是誤判，**When** 使用者移除該項，**Then** 該項不列入合計，且不會被儲存。
8. **Given** 使用者確認結果，**When** 點擊儲存，**Then** 系統建立一筆當日飲食紀錄（含各品項名稱、份量、熱量、營養素與餐別），並返回儀表板，今日已攝取熱量與剩餘熱量即時反映此筆紀錄。
9. **Given** 使用者在確認畫面選擇放棄，**When** 返回，**Then** 不建立任何紀錄，儀表板數值不變。

### User Story 3 - 每日熱量目標追蹤儀表板 (Priority: P3)

使用者進入主儀表板，看到當日的每日建議熱量、已攝取熱量與剩餘可用熱量，以及蛋白質、碳水化合物、脂肪的已攝取量與目標量，並可切換以「已攝取」或「尚缺」視角檢視。下方列出當日已建立的餐點紀錄。使用者可切換到近幾日的其他日期檢視該日的攝取狀況。

**Why this priority**: 儀表板是使用者每天回訪的落點，把散落的紀錄轉成「我今天還能吃多少」的可行動資訊。但它建立在已有目標值（US1）與已有紀錄（US2）之上，故排在其後。

**Independent Test**: 可獨立驗證——在已有目標值與若干筆紀錄的帳號上開啟儀表板，確認「建議熱量 − 已攝取 = 剩餘」與各營養素進度呈現正確，並可切換日期。

**Acceptance Scenarios**:

1. **Given** 使用者已有每日熱量目標且當日尚無任何紀錄，**When** 開啟儀表板，**Then** 已攝取顯示為 0、剩餘可用熱量等於每日建議熱量，並顯示尚無紀錄的空狀態提示。
2. **Given** 當日已有數筆飲食紀錄，**When** 開啟儀表板，**Then** 已攝取熱量等於當日所有紀錄品項熱量之總和，剩餘可用熱量等於建議熱量減去已攝取熱量。
3. **Given** 當日已攝取熱量超過每日建議熱量，**When** 檢視儀表板，**Then** 系統明確標示已超出目標，且剩餘可用熱量不顯示為負數以外的誤導性數值。
4. **Given** 使用者切換到「尚缺」檢視，**When** 畫面更新，**Then** 熱量與三大營養素改以「距離目標尚缺多少」呈現。
5. **Given** 使用者切換到前幾日的日期，**When** 畫面更新，**Then** 顯示該日的攝取狀況與該日紀錄清單，不影響當日資料。

### User Story 4 - 檢視飲食趨勢圖表 (Priority: P4)

使用者切換到趨勢頁面，以圖表檢視近 7／14／30 天的每日熱量攝取變化，並可切換檢視熱量、蛋白質、碳水化合物或脂肪，同時看到區間內的平均每日攝取與目標達成率等摘要數值。

**Why this priority**: 趨勢是留存與行為改變的關鍵，但屬於累積型價值——需要先有數天的紀錄才有意義，因此優先度低於單日流程。

**Independent Test**: 可獨立驗證——在已有多日紀錄的帳號上開啟趨勢頁，切換區間與指標，確認圖表與摘要數值和各日紀錄一致。

**Acceptance Scenarios**:

1. **Given** 使用者有連續數日的飲食紀錄，**When** 開啟趨勢頁並選擇近 7 天，**Then** 圖表呈現該區間每日的熱量攝取，且各日數值等於該日紀錄合計。
2. **Given** 使用者切換指標為蛋白質，**When** 圖表更新，**Then** 呈現同一區間的每日蛋白質攝取量。
3. **Given** 使用者切換區間為近 30 天，**When** 圖表更新，**Then** 呈現該區間資料；期間內沒有紀錄的日期以無攝取（零）呈現，而非中斷圖表或報錯。
4. **Given** 使用者尚無任何飲食紀錄，**When** 開啟趨勢頁，**Then** 顯示空狀態說明與引導建立第一筆紀錄的操作，而非空白或錯誤畫面。

### User Story 5 - 維護個人資訊與既有紀錄 (Priority: P5)

使用者可在個人設定頁檢視目前的身高、體重、年齡、活動量與計算出的每日目標，並修改個人資訊；修改後系統重新計算每日建議熱量與營養素目標。使用者也可編輯或刪除既有的飲食紀錄品項（修正份量、名稱或營養數值）。

**Why this priority**: 體重與活動量會隨時間變動，紀錄也難免記錯；沒有這層維護能力，資料會逐漸失真。但初次使用不會立刻需要，故排在最後。

**Independent Test**: 可獨立驗證——修改體重後確認每日建議熱量隨之變動；編輯一筆既有紀錄的份量後確認該日已攝取熱量隨之變動。

**Acceptance Scenarios**:

1. **Given** 使用者在設定頁修改體重，**When** 儲存，**Then** 系統以新數值重新計算每日建議熱量與三大營養素目標，並在儀表板反映新的目標值。
2. **Given** 使用者重新計算了目標值，**When** 檢視過去日期的儀表板，**Then** 歷史紀錄的攝取數值不因目標變動而改變。
3. **Given** 使用者編輯某筆既有紀錄的份量，**When** 儲存，**Then** 該筆的熱量與營養素依同一份量換算規則更新，且該日的已攝取與剩餘熱量同步更新。
4. **Given** 使用者刪除某筆飲食紀錄，**When** 確認刪除，**Then** 該筆自紀錄清單移除，該日合計與趨勢圖表同步扣除。

### Edge Cases

**AI 辨識相關**

- 照片中沒有可辨識的食物：辨識服務回傳空的品項清單與說明訊息，系統必須顯示引導畫面（說明未偵測到食物、提供「重新拍攝」與「返回」操作），不得嘗試呈現空的結果清單或空白畫面。
- 辨識請求逾時（超過系統設定的等待上限仍無回應）：顯示逾時說明與「重試」操作，使用者的照片不需重新選取即可重試。
- 辨識服務回傳伺服器錯誤、無法解析的回應、或服務暫時無法連線：顯示可理解的錯誤說明與「重試」操作，並在連續重試仍失敗時提供「返回」出口，避免使用者卡在錯誤畫面。
- 使用者在等待期間離開辨識畫面或關閉頁面：不建立任何紀錄，重新進入時回到乾淨狀態。
- 辨識出的食物在通用食物營養對照表中查無對應營養資料：該項仍列出名稱，但標示無法自動換算，使用者可自行填入熱量與營養素或移除該項。
- 辨識回傳的品項數量異常龐大：畫面需可捲動並維持逐項可調整，不因品項多而無法完成確認。

**上傳與權限相關**

- 使用者拒絕相機權限：系統改以相簿上傳作為替代路徑，並說明如何重新開啟權限，不阻斷整個記帳流程。
- 上傳的檔案不是圖片、或超過大小上限：在送出辨識前即提示並要求重新選擇。
- 上傳過程中網路中斷：顯示上傳失敗與重試操作。

**登入與環境相關**

- 執行環境判定為非 LINE 內時誤呼叫僅 LINE 內可用的功能：不得發生；所有 LINE 內專屬能力在非該環境下必須有對應的一般網頁替代路徑。
- 登入憑證過期或失效：使用者下一次操作時被導回登入流程，且完成登入後回到原本意圖的頁面。
- 使用者以同一 LINE 身分先後從 LIFF 與一般瀏覽器登入：視為同一使用者，看到同一份資料。

**資料與計算相關**

- 份量被調整為 0 或負值：不允許，份量必須為正數並受合理上下限約束。
- 個人資訊填入超出合理生理範圍的身高、體重或年齡：在送出前提示並要求修正。
- 紀錄跨越午夜建立：以使用者所在時區的日期歸屬，避免同一餐落入錯誤日期。
- 使用者同一天重複上傳同一張照片：允許，各自視為獨立紀錄（系統不做重複偵測）。

## Requirements *(mandatory)*

### Functional Requirements

**身分與登入**

- **FR-001**: 系統 MUST 以 LINE 登入作為唯一的身分驗證方式，不提供 Email 帳號密碼註冊或登入。
- **FR-002**: 系統 MUST 具備判斷「目前是否執行於 LINE 內建環境」的能力，並依判斷結果選擇對應的登入串接方式。
- **FR-003**: 在 LINE 內建環境中，系統 MUST 自動完成身分驗證，使用者無需額外輸入帳號資訊。
- **FR-004**: 在一般瀏覽器環境中，系統 MUST 提供使用者主動觸發的 LINE 授權登入流程，並在授權完成後回到原本欲前往的頁面。
- **FR-005**: 系統 MUST NOT 在任何程式路徑上預設一定執行於 LINE 內建環境；所有 LINE 內專屬能力在非該環境下 MUST 有對應的一般網頁替代路徑或明確的降級行為。
- **FR-006**: 後端 MUST 以同一套驗證邏輯處理來自所有入口的登入憑證，不因入口不同而分岔驗證路徑。
- **FR-007**: 系統 MUST 將同一 LINE 身分在不同入口的登入視為同一使用者，並提供同一份資料。
- **FR-008**: 當使用者的登入狀態失效時，系統 MUST 導回登入流程並在完成後恢復原操作情境，不顯示錯誤或空白畫面。

**個人健康檔案與每日目標**

- **FR-009**: 系統 MUST 允許使用者建立與維護個人健康檔案，欄位包含性別、年齡、身高、體重與日常活動量等級。
- **FR-010**: 系統 MUST 提供至少三種日常活動量等級（低／中／高），並附可理解的說明供使用者判斷。
- **FR-011**: 系統 MUST 於個人健康檔案完成時計算基礎代謝率（BMR）與每日總消耗熱量（TDEE），並以 TDEE 作為每日建議熱量。
- **FR-012**: 系統 MUST 依每日建議熱量推導蛋白質、碳水化合物與脂肪的每日目標量，並向使用者呈現。
- **FR-013**: 系統 MUST 在使用者尚未完成個人健康檔案前，將其導向填寫流程，不允許進入主儀表板。
- **FR-014**: 系統 MUST 驗證個人資訊輸入落在合理生理範圍內，超出範圍時在送出前提示並要求修正。
- **FR-015**: 使用者 MUST 能修改既有個人健康檔案；修改後系統 MUST 重新計算每日建議熱量與營養素目標。
- **FR-016**: 重新計算目標值 MUST NOT 變更任何已儲存的歷史飲食紀錄數值。

**照片上傳**

- **FR-017**: 系統 MUST 提供「使用相機即時拍照」與「從相簿選取照片」兩種上傳來源，兩者進入同一套辨識流程。
- **FR-018**: 系統 MUST 在使用者拒絕相機權限時提供相簿上傳作為替代路徑，並說明如何重新開啟權限。
- **FR-019**: 系統 MUST 在送出辨識前驗證檔案類型與大小，不符時提示並要求重新選擇。

**AI 辨識串接與結果呈現**

- **FR-020**: 系統 MUST 將使用者提供的照片送交辨識服務，取得照片中偵測到的食物品項清單。
- **FR-021**: 系統 MUST 對每個辨識出的食物品項，自通用食物營養對照表取得該食物每 100 公克的熱量、蛋白質、碳水化合物與脂肪數值。
- **FR-022**: 系統 MUST 對每個食物品項套用一組由後端設定的「預設份量（公克）」作為初始估計值；此預設份量為系統設定值，MUST NOT 被描述或呈現為模型量測結果。
- **FR-023**: 系統 MUST 以「每 100 公克數值 × (份量公克數 ÷ 100)」計算每個品項的熱量與三大營養素。
- **FR-024**: 系統 MUST 在辨識結果畫面逐項呈現食物名稱、份量、熱量與三大營養素，並呈現本次紀錄的合計值。
- **FR-025**: 系統 MUST 在辨識請求送出後至結果返回前，持續顯示明確的進行中狀態。
- **FR-026**: 系統 MUST 防止使用者在同一次辨識尚未完成時重複送出相同請求。
- **FR-027**: 當辨識服務回傳的品項清單為空時，系統 MUST 顯示未偵測到食物的引導畫面（含服務回傳的說明訊息、「重新拍攝」與「返回」操作），MUST NOT 呈現空的結果清單。
- **FR-028**: 系統 MUST 對辨識逾時、伺服器錯誤、連線失敗與無法解析的回應各自提供可理解的錯誤說明與重試操作；重試 MUST NOT 要求使用者重新選取照片。
- **FR-029**: 系統 MUST 在連續重試仍失敗時提供明確的返回出口，避免使用者無法離開錯誤狀態。
- **FR-030**: 使用者取消或離開辨識流程時，系統 MUST NOT 建立任何飲食紀錄。

**份量即時調整（核心互動）**

- **FR-031**: 辨識結果畫面上的「份量」欄位 MUST 是帶有預設值且可由使用者即時互動調整的元件（滑桿或數值輸入）。
- **FR-032**: 使用者調整份量時，該品項的熱量與三大營養素 MUST 即時重新計算並更新顯示，MUST NOT 要求使用者另外觸發「重新計算」或重新送出辨識。
- **FR-033**: 任一品項份量變動時，本次紀錄的合計熱量與營養素 MUST 同步更新。
- **FR-034**: 份量 MUST 限制為正數並受合理上下限約束，超出範圍時不接受該輸入。

**辨識結果修正**

- **FR-035**: 系統 MUST 提供辨識服務給出的其他候選食物名稱（依信心度排序）供使用者改選；改選後 MUST 以新食物的每 100 公克營養值與預設份量重新換算。
- **FR-036**: 使用者 MUST 能移除辨識結果中的誤判品項；被移除的品項不列入合計亦不被儲存。
- **FR-037**: 使用者 MUST 能手動修正品項的食物名稱與營養數值；當名稱在通用食物營養對照表中查無對應資料時，系統 MUST 標示無法自動換算，並允許使用者自行填入或移除該項。
- **FR-038**: 系統 MUST 允許使用者為本次紀錄指定餐別（早餐／午餐／晚餐／點心），並依當下時間提供預設值。

**紀錄儲存與維護**

- **FR-039**: 系統 MUST 在使用者確認後儲存飲食紀錄，內容包含各品項的食物名稱、份量、熱量、三大營養素、餐別、建立時間與所屬日期。
- **FR-040**: 系統 MUST 以使用者所在時區的日期決定紀錄的歸屬日期。
- **FR-041**: 儲存完成後系統 MUST 返回儀表板，且當日已攝取與剩餘熱量、當日紀錄清單 MUST 即時反映該筆紀錄，無需使用者手動重新整理。
- **FR-042**: 使用者 MUST 能編輯既有飲食紀錄的品項名稱、份量與營養數值；編輯後該日合計 MUST 同步更新。
- **FR-043**: 使用者 MUST 能刪除既有飲食紀錄；刪除後該日合計與趨勢圖表 MUST 同步扣除。
- **FR-044**: 所有飲食紀錄 MUST 歸屬於建立它的使用者，且使用者 MUST NOT 能存取他人的紀錄。

**儀表板**

- **FR-045**: 儀表板 MUST 顯示當日的每日建議熱量、已攝取熱量與剩餘可用熱量（剩餘 = 建議 − 已攝取）。
- **FR-046**: 儀表板 MUST 顯示蛋白質、碳水化合物與脂肪的已攝取量與目標量。
- **FR-047**: 儀表板 MUST 提供「已攝取」與「尚缺」兩種檢視視角的切換。
- **FR-048**: 當已攝取熱量超過每日建議熱量時，儀表板 MUST 明確標示已超出目標。
- **FR-049**: 儀表板 MUST 列出所選日期的飲食紀錄清單，並在無紀錄時顯示空狀態提示。
- **FR-050**: 使用者 MUST 能切換檢視日期，查看其他日期的攝取狀況。

**趨勢圖表**

- **FR-051**: 系統 MUST 提供近 7 天、14 天與 30 天三種區間的攝取趨勢圖表。
- **FR-052**: 趨勢圖表 MUST 支援切換檢視熱量、蛋白質、碳水化合物與脂肪四種指標。
- **FR-053**: 趨勢圖表 MUST 顯示區間內的摘要數值，至少包含平均每日攝取量與目標達成率。
- **FR-054**: 區間內沒有紀錄的日期 MUST 以零攝取呈現，不得中斷圖表或產生錯誤。
- **FR-055**: 使用者尚無任何紀錄時，趨勢頁 MUST 顯示空狀態說明與引導建立第一筆紀錄的操作。

**資料隔離與免責**

- **FR-056**: 本輪使用的通用食物營養對照表 MUST 為獨立資料集，MUST NOT 與特定店家／餐點營養資料共用同一份資料表。
- **FR-057**: 系統 MUST 在呈現辨識結果與營養數據的介面明確傳達其為估算值。
- **FR-058**: 系統 MUST NOT 提供疾病判讀、過敏判斷、處方或任何醫療級營養診斷與治療建議，亦 MUST NOT 以文案或介面暗示其結果具醫療效力。

### Key Entities

- **使用者（User）**：以 LINE 身分識別的服務使用者。屬性包含 LINE 身分識別碼、顯示名稱、頭像、建立時間。一位使用者對應一份個人健康檔案與多筆飲食紀錄。本輪所有使用者皆為一般使用者角色（管理員角色屬後續輪次）。
- **個人健康檔案（HealthProfile）**：使用者的生理基本資料與活動量。屬性包含性別、年齡、身高、體重、活動量等級、最後更新時間。為計算 BMR／TDEE 的輸入。
- **每日目標（DailyTarget）**：由個人健康檔案推導出的每日建議熱量與三大營養素目標量。隨個人健康檔案更新而重新計算，歷史紀錄不受影響。
- **飲食紀錄（MealRecord）**：使用者的一次記帳，對應一次拍照辨識或一次手動修正的結果。屬性包含所屬使用者、歸屬日期、餐別、建立時間、來源照片、合計熱量與營養素。一筆紀錄包含一至多個紀錄品項。
- **紀錄品項（MealItem）**：飲食紀錄中的單一食物項目。屬性包含食物名稱、對應的通用食物參照（可為空，代表使用者自行輸入）、份量公克數、換算後的熱量與三大營養素、是否經使用者修正。
- **通用食物營養對照表（FoodNutritionReference）**：供拍照辨識使用的通用食物營養資料。屬性包含食物名稱、對應的辨識分類標籤、每 100 公克的熱量與蛋白質／碳水／脂肪、系統設定的預設份量公克數。此資料集與店家餐點營養資料完全獨立。
- **辨識結果（RecognitionResult）**：一次辨識請求的回傳內容。包含偵測到的品項清單（每項含候選食物名稱與其信心度排序、在照片中的位置）與服務訊息；品項清單可為空，代表未偵測到食物。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新使用者自點擊入口至看到自己的每日建議熱量，中位數耗時不超過 2 分鐘，且完成率不低於 90%。
- **SC-002**: 使用者自選擇照片至完成儲存一筆飲食紀錄，所需操作步驟不超過 5 步。
- **SC-003**: 使用者調整份量後，畫面上的熱量與營養素在使用者感受上即時更新（0.3 秒內），且全程無需按下任何額外的重新計算操作。
- **SC-004**: 辨識等待期間 100% 的時間顯示明確的進行中狀態；未偵測到食物、逾時、伺服器錯誤三類情境皆有對應說明與可執行的下一步，不出現空白或無回應畫面。
- **SC-005**: 儲存紀錄後返回儀表板時，當日已攝取熱量、剩餘可用熱量與紀錄清單皆已反映該筆紀錄，使用者無需手動重新整理。
- **SC-006**: 同一位使用者在 LINE 內與一般瀏覽器兩種入口皆能完成本輪全部流程，且看到的資料與計算結果一致。
- **SC-007**: 未經教學的新使用者中，至少 90% 能在首次嘗試即成功完成一筆拍照飲食紀錄。
- **SC-008**: 有連續紀錄的使用者可查看近 7／14／30 天趨勢，且圖表各日數值與該日紀錄合計完全一致。
- **SC-009**: 使用者無法透過任何操作看到他人的飲食紀錄或個人健康檔案。

## Assumptions

以下為在使用者描述未明確指定時，依產品企劃書、原型與產業慣例所採用的合理預設。若與實際期待不符，應於 `/speckit.clarify` 階段修正。

**個人資訊與計算**

- 個人健康檔案包含「性別」欄位：使用者列出的欄位為年齡／身高／體重／活動量，但業界標準的 BMR 公式需要性別作為輸入，且原型的填寫流程已包含此欄位，故納入。
- BMR 採 Mifflin-St Jeor 公式，TDEE 為 BMR 乘上活動量係數；活動量分為低／中／高三級，與原型一致。實際係數與營養素分配比例屬實作細節，於 plan 階段確定。
- 每日熱量目標即等於 TDEE。本輪不提供「減脂／增肌目標」等會調整目標熱量的設定，亦不提供目標體重設定。
- 三大營養素目標由每日建議熱量與體重推導，不由使用者手動指定。

**辨識與份量**

- 辨識模型已訓練完成，本輪僅需串接，不含模型訓練、微調或準確度優化工作。
- 辨識服務與後端部署於同一台伺服器，後端視其為內部服務呼叫，不涉及跨網域或第三方代管端點。
- 本輪以「後端同步等待辨識服務回應」作為預設設計。此為暫定假設而非最終架構決定——呼叫方式（同步／非同步）與回應時間預期尚未確認，plan 階段必須將其列為 open question，並保留未來改為非同步（輪詢或推送）而不需重寫前端流程的彈性。
- 辨識等待上限暫定為 30 秒；超過即視為逾時並進入逾時處理流程。此數值待實際回應時間確認後於 plan 階段調整。
- 每個可辨識的食物分類在通用食物營養對照表中都應有對應的每 100 公克營養值與預設份量。本輪需建立此資料表結構並匯入涵蓋模型輸出分類的資料；資料來源與涵蓋範圍待確認。
- 「預設份量」由後端設定並可調整，不同食物可有不同預設值（例如滷肉飯 250 公克）。

**功能邊界**

- 本輪的「手動修正」指辨識結果確認畫面上的修正，以及已儲存紀錄的編輯與刪除。不含「從零手動搜尋食物資料庫新增品項」與條碼掃描——兩者皆屬後續輪次。
- 本輪不含推薦餐廳模組，因此不需要店家／餐點資料、地理定位或距離排序能力。
- 本輪不含管理員角色與後台維護介面；通用食物營養對照表的資料維護於本輪以直接匯入方式處理，管理介面屬後續輪次。惟後端的權限設計不得妨礙後續加入僅管理員可通過的權限檢查層。
- 本輪不含 Flutter iOS／Android 客戶端；但後端 API 的設計必須能在不分岔驗證邏輯的前提下服務後續加入的原生客戶端。
- 本輪不含 LINE 訊息推播。

**環境與資料**

- 使用者具備可正常連線的網路環境；客戶端不保留離線資料，所有資料即時取自後端。
- 原型檔案僅作為視覺與互動風格的參考來源，其中的示範資料、硬編碼數值與程式結構不構成需求。
- 使用者的個人健康資料屬個人資料，其蒐集與利用需符合個人資料保護相關法規要求。
