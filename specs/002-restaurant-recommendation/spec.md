## 本輪範圍界線

**包含**：LIFF 入口的推薦餐廳模組——定位權限請求與取得目前座標、依座標計算距離並排序回傳最近 10 家店家、店家餐點清單瀏覽（每項餐點顯示熱量與三大營養素）、定位被拒／定位失敗／查無店家三類情境的替代畫面、供本輪驗證用的店家與餐點測試資料。

**沿用第一輪既有實作（不重新設計亦不修改）**：使用者資料表、LINE Login 身分驗證邏輯、後端 API 架構與錯誤處理慣例、既有視覺風格（色彩、字體、圓角、深色模式）。

**排除（第三輪管理員後台）**：店家與餐點的新增、編輯、刪除介面；管理員角色與權限；資料的寫入由第三輪負責，本輪只提供唯讀查詢。

**排除（其他入口）**：一般網頁、iOS App、Android App 三個入口不實作推薦餐廳的任何畫面。

**排除（不列入本產品）**：合作店家點餐流程、訂單系統 API 串接。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 授權定位並看到附近最近的店家 (Priority: P1)

使用者在 LINE 內（LIFF）開啟服務，從主導覽進入「推薦餐廳」。首次進入時，系統以與第一輪相機權限相同的請求模式，向使用者請求「目前位置」權限並說明用途。使用者允許後，系統取得目前座標並送交後端；後端以該座標對店家清單逐一計算距離、由近至遠排序，回傳最近的 10 家。畫面以清單呈現這些店家，每家顯示店名、地址與距離，依距離由近至遠排列。

**Why this priority**: 「依目前位置找到附近可吃的店」是本模組的核心價值主張，也是其他畫面的入口。沒有這條路徑，店家與餐點資料對使用者而言不可及。

**Independent Test**: 可獨立驗證——在 LIFF 內以已 seed 的測試店家資料走一次「進入推薦餐廳 → 允許定位 → 看到依距離排序的店家清單」，即使尚未實作餐點瀏覽，使用者也已獲得「附近有哪些店家」的價值。

**Acceptance Scenarios**:

1. **Given** 使用者在 LINE 內（LIFF）已登入且尚未授權定位權限，**When** 進入推薦餐廳頁，**Then** 系統顯示定位權限請求（含用途說明），請求模式與第一輪相機權限一致。
2. **Given** 使用者允許定位權限，**When** 系統成功取得目前座標，**Then** 畫面顯示 5 公里範圍內、依距離由近至遠排序的店家清單，且筆數不超過 10 筆。
3. **Given** 使用者 5 公里範圍內的店家多於 10 家，**When** 清單回傳，**Then** 僅呈現距離最近的 10 家，其餘不呈現。
4. **Given** 使用者 5 公里範圍內的店家少於 10 家，**When** 清單回傳，**Then** 呈現該範圍內全部店家並依距離由近至遠排序，不以超出 5 公里的店家或空白項目補足至 10 筆。
5. **Given** 資料庫中有店家資料，但沒有任何一家位於使用者 5 公里範圍內，**When** 清單回傳，**Then** 顯示「附近查無店家」的空狀態說明與「改看全部店家」操作；使用者點擊後看到不受 5 公里限制、不顯示距離的全部店家清單。
6. **Given** 清單已呈現，**When** 使用者檢視任一店家項目，**Then** 該項顯示店名、地址，以及該店與使用者目前位置的距離。
7. **Given** 使用者已授權定位且清單已載入，**When** 使用者重新載入或再次進入該頁，**Then** 系統以當下取得的座標重新計算排序，不沿用前一次的座標結果。

### User Story 2 - 瀏覽店家餐點的熱量與營養素 (Priority: P2)

使用者在店家清單中點選一家店，進入該店的餐點瀏覽畫面。畫面顯示該店名稱與其登錄的餐點清單，每一項餐點呈現餐點名稱、熱量與蛋白質、碳水化合物、脂肪三大營養素數值。使用者可捲動瀏覽整份餐點清單，並返回店家清單改看其他店家。

**Why this priority**: 餐點營養資訊是使用者決定「這家店我能不能吃、該點什麼」的依據，是店家清單之後的必要下一步；但它建立在已能找到店家（US1）之上，故排在其後。

**Independent Test**: 可獨立驗證——在已 seed 的店家資料上點選任一家店，確認該店餐點逐項顯示熱量與三大營養素，且數值與該店登錄的資料一致。

**Acceptance Scenarios**:

1. **Given** 店家清單已呈現，**When** 使用者點選其中一家店，**Then** 進入該店的餐點瀏覽畫面並顯示該店名稱。
2. **Given** 使用者進入某店的餐點畫面，**When** 該店已登錄多筆餐點，**Then** 逐項列出每筆餐點的名稱、熱量與蛋白質／碳水化合物／脂肪數值。
3. **Given** 某店尚未登錄任何餐點，**When** 使用者進入該店餐點畫面，**Then** 顯示「此店家尚未提供餐點資訊」的空狀態說明與返回操作，而非空白畫面或錯誤畫面。
4. **Given** 使用者正在瀏覽某店餐點，**When** 使用者選擇返回，**Then** 回到店家清單且清單維持原先的排序結果，不重新請求定位權限。
5. **Given** 餐點畫面呈現營養數值，**When** 使用者檢視，**Then** 畫面明確傳達這些數值為估算參考值。

---

### User Story 3 - 定位不可用時仍可瀏覽店家 (Priority: P3)

使用者拒絕定位權限，或裝置的定位服務本身不可用（定位功能關閉、GPS 訊號取得失敗）。系統不中斷推薦餐廳模組，改以「全部店家清單」呈現，不做距離排序、不顯示距離；畫面同時說明目前為何無法依距離推薦，以及使用者可如何重新啟用定位。使用者仍可點選任一店家瀏覽其餐點。

**Why this priority**: 這是保障模組可用性的降級路徑——定位被拒或失敗是常見情境，缺少此路徑會讓相當比例的使用者完全無法使用本模組。但它是主要流程的替代方案，故排在其後。

**Independent Test**: 可獨立驗證——分別以「拒絕權限」與「關閉裝置定位服務」兩種狀態進入推薦餐廳，確認兩者各自顯示對應說明、皆呈現全部店家清單，且皆可進入餐點瀏覽。

**Acceptance Scenarios**:

1. **Given** 使用者拒絕定位權限，**When** 系統偵測到拒絕，**Then** 顯示「已拒絕定位權限」的說明與重新開啟權限的指引，並呈現全部店家清單（不排序、不顯示距離）。
2. **Given** 使用者的裝置定位服務關閉或 GPS 訊號取得失敗，**When** 系統偵測到取得座標失敗，**Then** 顯示與「拒絕權限」不同的說明文案（指向裝置定位設定或訊號問題）並提供「重試定位」操作，同時呈現全部店家清單。
3. **Given** 系統因定位失敗而顯示重試操作，**When** 使用者點擊重試且此次成功取得座標，**Then** 畫面切換為依距離排序的最近店家清單。
4. **Given** 目前為全部店家清單（無距離）狀態，**When** 使用者點選任一店家，**Then** 仍可正常進入該店的餐點瀏覽畫面。
5. **Given** 資料庫中完全沒有任何店家資料，**When** 使用者進入推薦餐廳頁（無論定位是否成功），**Then** 顯示「目前尚無店家資料」的空狀態說明，而非空白清單或錯誤畫面。

### Edge Cases

**定位與權限相關**

- 使用者拒絕定位權限：不阻斷模組，退回全部店家清單（不排序、不顯示距離），並提供重新開啟權限的說明。此情境與定位服務失敗必須以**不同**的說明文案分別處理。
- 裝置定位服務關閉或 GPS 訊號取得失敗（權限已授權但取不到座標）：顯示指向裝置設定／訊號的說明與「重試定位」操作，同時退回全部店家清單。
- 取得座標逾時（權限已授權，但在系統設定的等待上限內仍未回傳座標）：視同定位服務失敗處理，顯示重試操作，不無限期停留在載入狀態。
- 使用者先前已拒絕權限，之後於裝置設定中重新開啟：再次進入或點擊重試時，系統應能取得座標並切換為距離排序清單。
- 取得的座標明顯不合理（超出有效經緯度範圍）：視同定位失敗處理，不以錯誤座標計算距離而產生誤導性的排序結果。

**資料與清單相關**

- 附近查無店家（資料庫有店家，但最近的一家仍超出 5 公里）：顯示「附近查無店家」的空狀態說明，並提供「改看全部店家」操作。此情境與「資料庫完全無店家資料」的文案應可區分。
- 5 公里內的店家不足 10 家：僅呈現範圍內的店家，不以第 11 公里處的店家補滿名額；清單筆數少於 10 筆屬正常結果，不視為錯誤或空狀態。
- 店家資料缺少經緯度：後台允許只建立「名稱＋地址」而暫不填座標的店家，故此為**常態資料**而非異常。該店不參與距離計算與最近 10 家排序（沒有距離可算，補在清單末端會讓使用者要求「附近」時混入與距離無關的店家）；但在不排序的全部店家清單中 MUST 正常出現——即定位被拒或定位失敗的那條路徑仍看得到這些店家。
- 店家的地址與座標不一致：系統不驗證兩者是否相符，距離一律以座標為準，地址僅供顯示。
- 多家店名完全相同（連鎖分店）：屬正常資料，各自為獨立店家，以地址區分並以識別碼查詢，不得合併或去重。
- 同一店家內有同名餐點：屬正常資料，各自獨立列出，不得去重。不同店家的同名餐點數值互不連動。
- 店家尚未登錄任何餐點：餐點畫面顯示空狀態說明與返回操作。
- 某項餐點的營養欄位缺值：該項仍列出名稱，缺值欄位以明確的「無資料」呈現，不以 0 呈現（0 會被誤讀為「不含該營養素」）；反之數值確實為 0 時正常顯示 0，不呈現為「無資料」。
- 使用者停留在餐點畫面期間，該店家已由第三輪後台刪除：刪除為實刪除且連帶刪除其餐點，使用者的下一次操作應得到「此店家已不存在」的說明並可返回清單，不出現無法離開的錯誤畫面。

**入口與環境相關**

- 使用者以一般網頁、iOS App 或 Android App 進入服務：不呈現推薦餐廳的任何入口或畫面；其他既有功能不受影響，且不因缺少本模組而出現錯誤或空白畫面。
- 未登入或登入狀態失效的請求存取店家／餐點查詢：比照第一輪既有的驗證與導回登入行為處理。

## Requirements *(mandatory)*

### Functional Requirements

**入口與環境限定**

- **FR-001**: 推薦餐廳模組（定位、店家清單、餐點瀏覽）的使用者介面 MUST 僅於 LIFF 入口提供。
- **FR-002**: 系統 MUST 在一般網頁、iOS App 與 Android App 三個入口不呈現推薦餐廳的任何入口、導覽項目或畫面。
- **FR-003**: 系統 MUST 以既有的執行環境偵測能力判斷是否為 LIFF 環境來決定是否顯示本模組入口，MUST NOT 在非 LIFF 環境下因缺少本模組而使頁面錯誤或空白。
- **FR-004**: 店家與餐點查詢 MUST 沿用第一輪既有的 LINE Login 身分驗證邏輯，MUST NOT 為本模組分岔出獨立的驗證路徑或入口專用端點。

**定位權限與座標取得**

- **FR-005**: 系統 MUST 於使用者進入推薦餐廳模組時向其請求「目前位置」權限，請求模式 MUST 比照第一輪相機權限的請求模式（含用途說明）。
- **FR-006**: 系統 MUST 在取得使用者授權後讀取目前座標（緯度、經度），並以該座標作為距離計算的輸入。
- **FR-007**: 系統 MUST 區分「使用者拒絕授權」與「定位服務失敗（裝置定位關閉、GPS 訊號問題、取得逾時、座標無效）」兩類情境，並分別提供各自的說明文案與畫面行為。
- **FR-008**: 當使用者拒絕授權時，系統 MUST 顯示全部店家清單作為替代方案，不做距離排序、不顯示距離，並 MUST 提供重新開啟權限的說明。
- **FR-009**: 當定位服務失敗時，系統 MUST 顯示指向裝置定位設定或訊號問題的說明、MUST 提供「重試定位」操作，並同時顯示全部店家清單作為替代方案。
- **FR-010**: 系統 MUST 為座標取得設定等待上限，超過即視為定位服務失敗並進入對應流程，MUST NOT 無限期停留在載入狀態。
- **FR-011**: 系統 MUST 在使用者重試定位成功後，將畫面切換為依距離排序的最近店家清單，無需使用者重新進入頁面。
- **FR-012**: 系統 MUST NOT 儲存或保留使用者的定位座標作為長期資料；座標僅用於本次查詢的距離計算。

**店家清單與距離排序**

- **FR-013**: 後端 MUST 接受使用者目前座標作為查詢輸入，對店家逐一計算其與該座標的距離。
- **FR-014**: 後端 MUST 依距離由近至遠排序，並回傳最近的 10 家店家；符合條件的店家少於 10 家時回傳全部。
- **FR-015**: 距離計算 MUST 以既有技術棧內的計算方式完成，MUST NOT 為此引入額外的地理資訊資料庫或空間索引擴充套件（店家數量不大，計算單純）。
- **FR-016**: 店家清單的每一項 MUST 顯示店名與地址；在距離排序模式下 MUST 另顯示該店與使用者目前位置的距離。地址為必要顯示欄位而非裝飾——店家名稱不具唯一性（連鎖分店同名，以地址區分），缺少地址時使用者無法辨別是哪一家分店。
- **FR-016a**: 系統 MUST 以店家識別碼（而非店家名稱）作為清單項目的識別與後續查詢的依據，MUST NOT 假設店家名稱或餐點名稱唯一。
- **FR-017**: 系統 MUST 提供不帶座標的全部店家清單查詢，供定位被拒或定位失敗時使用；此清單 MUST NOT 顯示距離欄位。
- **FR-018**: 缺少經緯度或經緯度無效的店家 MUST NOT 參與距離計算與最近 10 家排序，但 MUST 正常出現在不排序的全部店家清單中（FR-017）。座標為選填欄位，缺座標的店家屬常態資料。
- **FR-018a**: 系統 MUST NOT 對店家或餐點套用任何「排除已刪除」的過濾條件。刪除為實刪除（資料表無軟刪除或上下架欄位），已刪除的資料不會出現在查詢結果中；額外的過濾條件只會成為未來的錯誤來源。
- **FR-019**: 當依距離查無店家時（5 公里半徑內無任何有效座標店家），系統 MUST 顯示「附近查無店家」的空狀態說明，並 MUST 提供「改看全部店家」操作；該操作 MUST 呈現不受 5 公里限制的全部店家清單，並比照 FR-017 不顯示距離。此空狀態文案 MUST 與「資料庫尚無任何店家資料」的空狀態可區分。
- **FR-020**: 「附近」的距離範圍上限為 5 公里；距離使用者目前位置超過 5 公里的店家 MUST NOT 出現在距離排序清單中，即使 5 公里內的店家不足 10 家，亦 MUST NOT 以超出範圍的店家補足。

**店家餐點瀏覽**

- **FR-021**: 使用者 MUST 能自店家清單點選任一店家，進入該店家的餐點瀏覽畫面。
- **FR-022**: 餐點瀏覽畫面 MUST 顯示該店家名稱與其登錄的餐點清單。
- **FR-023**: 每一項餐點 MUST 顯示餐點名稱、熱量與蛋白質、碳水化合物、脂肪三項營養素數值。
- **FR-024**: 當店家尚未登錄任何餐點時，系統 MUST 顯示空狀態說明與返回操作，MUST NOT 呈現空白或錯誤畫面。
- **FR-025**: 系統 MUST 區分「營養欄位缺值」與「數值為 0」兩種狀態：缺值 MUST 以明確的「無資料」呈現且 MUST NOT 以 0 呈現；數值確實為 0 時 MUST 正常顯示為 0 且 MUST NOT 呈現為「無資料」。（0 代表店家登錄該營養素為零，缺值代表店家未提供，兩者對使用者的意義不同。）
- **FR-026**: 使用者自餐點畫面返回時，店家清單 MUST 維持原先的排序結果，且 MUST NOT 重新請求定位權限。
- **FR-027**: 當使用者存取的店家已不存在時，系統 MUST 顯示可理解的說明與返回清單的操作。

**資料範圍與資料模型隔離**

- **FR-028**: 店家與餐點資料表的欄位 MUST 完全依照共用契約（[reference/shared-schema-store-menu.md](../../reference/shared-schema-store-menu.md)，2026-08-04 第三輪交接更新）：`stores`（id、name、address、latitude、longitude、created_at、updated_at）與 `menu_items`（id、store_id、name、calories、protein_g、carbs_g、fat_g、created_at、updated_at）。本輪 MUST NOT 自行增減欄位或修改欄位名稱。資料表的 DDL 由第三輪建立，本輪 MUST NOT 提供建表 migration。`menu_items` 的時間戳由第三輪寫入端自動填寫，本輪不讀取亦不對外呈現。
- **FR-029**: 本輪 MUST 僅提供店家與餐點的唯讀查詢能力；MUST NOT 提供新增、修改或刪除店家／餐點的介面或寫入端點（屬第三輪管理員後台範圍）。
- **FR-030**: 店家餐點營養資料 MUST 為與第一輪通用食物營養對照表完全獨立的資料集；系統 MUST NOT 在兩者間建立關聯、共用資料表或以任一方的數值替代另一方。
- **FR-031**: 即使某餐點名稱與通用食物營養對照表中的食物名稱相同，系統 MUST 一律採用該店家登錄的營養數值，MUST NOT 查詢或連動通用食物營養對照表。
- **FR-032**: 本輪 MUST NOT 修改第一輪既有的使用者資料表、LINE Login 驗證邏輯與既有 API 端點的行為。

**測試資料**

- **FR-033**: 本輪 MUST 隨資料表建立提供測試用的店家與餐點資料（透過 seed 腳本或 migration 附帶），使定位排序、清單顯示與餐點瀏覽可在第三輪管理介面完成前即完成驗證。
- **FR-034**: 測試資料 MUST 涵蓋足以驗證本輪驗收情境的組合，至少包含：同一參考座標 5 公里內多於 10 家的店家（驗證取最近 10 家）、彼此距離足以區分排序的座標分布、至少一家距該參考座標超過 5 公里的店家（驗證半徑排除與「改看全部店家」路徑）、至少一家已登錄多筆餐點的店家、至少一家尚未登錄餐點的店家。
- **FR-035**: 測試資料 MUST 可明確識別為測試資料，且其載入方式 MUST NOT 妨礙第三輪後台之後寫入正式資料。

**視覺一致性與免責**

- **FR-036**: 本模組的畫面 MUST 延續第一輪已確立的視覺風格（色彩、字體、圓角、深色模式），版面配置依既有頁面風格延伸設計。
- **FR-037**: 呈現餐點營養數據的介面 MUST 明確傳達其為估算參考值。
- **FR-038**: 本模組 MUST NOT 提供疾病判讀、過敏判斷或任何醫療級營養診斷與治療建議，亦 MUST NOT 以文案或介面暗示其結果具醫療效力。

### Key Entities

- **店家（Store）**：收錄的餐飲店家。屬性包含店家名稱、地址、緯度、經度、建立時間、更新時間。一家店家對應零至多筆餐點。欄位定義以共用契約為準，本輪不得變更；本輪對其僅有讀取權限，寫入由第三輪管理員後台負責。
- **餐點（MenuItem）**：店家登錄的單一餐點及其營養數值。屬性包含所屬店家、餐點名稱、熱量、蛋白質、碳水化合物、脂肪。此資料與第一輪的通用食物營養對照表完全獨立，即使名稱相同亦不共用數值。欄位定義以共用契約為準，本輪不得變更。
- **使用者目前位置（UserLocation）**：使用者在單次查詢當下的緯度與經度，由裝置定位取得。屬於暫時性的查詢輸入，不作為長期資料保存。
- **店家距離（StoreDistance）**：某店家與使用者目前位置之間的距離，為查詢時計算得出的衍生值，不儲存於資料表。作為最近 10 家清單的排序依據與清單顯示欄位。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者自 LIFF 內進入推薦餐廳至看到附近店家清單，在授權定位的情況下不超過 3 個操作步驟。
- **SC-002**: 已授權定位的使用者，看到的店家清單筆數不超過 10 筆、每一筆距離皆不超過 5 公里，且每一筆的距離皆不大於下一筆（排序完全正確）。
- **SC-003**: 使用者自店家清單點選一家店至看到該店餐點的熱量與三大營養素，不超過 1 個操作步驟。
- **SC-004**: 定位權限被拒、定位服務失敗、附近查無店家、資料庫無店家資料、店家無餐點五類情境，100% 皆有各自可區分的說明文案與可執行的下一步操作，不出現空白、無回應或無法離開的畫面。
- **SC-005**: 定位權限被拒與定位服務失敗兩類情境的說明文案與可用操作可被使用者區分（前者指向權限設定，後者指向裝置定位設定並提供重試）。
- **SC-006**: 在一般網頁、iOS App 與 Android App 三個入口，推薦餐廳的入口與畫面 0% 可被觸及，且三個入口的既有功能不因本模組而發生錯誤。
- **SC-007**: 店家清單與餐點清單在使用者感受上即時載入（一般網路條件下 2 秒內完成呈現）。
- **SC-008**: 餐點畫面呈現的營養數值與該店家登錄的數值 100% 一致，且與通用食物營養對照表的同名食物數值互不影響（修改任一方不改變另一方的呈現結果）。
- **SC-009**: 建立的店家／餐點資料表欄位與共用契約 100% 一致（欄位名稱與數量無增減），可與第三輪分支合併而不產生 schema 衝突。
- **SC-010**: 本輪功能可在第三輪管理介面尚未完成的情況下，僅憑本輪提供的測試資料完成全部驗收情境驗證。

## Assumptions

以下為在規格說明未明確指定時，依第一輪既有實作、專案憲章與產業慣例所採用的合理預設。若與實際期待不符，應於 `/speckit-clarify` 階段修正。

**入口限定與 API 設計**

- 「僅於 LIFF 入口提供」的限制實作於**使用者介面層**：僅 LIFF 環境呈現本模組的入口與畫面。後端查詢 API 不因入口而分岔——依專案憲章「後端 API 契約對四端一致」與「單一驗證實作」，本輪不建立入口專用端點，亦不在後端以入口來源阻擋請求。若需在後端限制僅 LIFF 來源可查詢，屬額外的安全需求，須另行確認。
- 店家與餐點查詢比照第一輪既有端點要求登入狀態；未登入或登入失效的處理沿用第一輪既有行為。

**定位與距離**

- 定位權限透過裝置／瀏覽器既有的位置權限機制取得，請求時機為使用者主動進入推薦餐廳模組時（而非服務啟動時），與第一輪相機權限的請求時機一致。
- 距離以直線距離（大圓距離）計算，非實際道路行駛或步行距離。5 公里的半徑上限亦以直線距離認定，實際步行或車行距離會大於此值。本輪不串接任何路徑規劃或導航服務。
- 5 公里半徑上限為固定值，不由使用者調整，亦不依店家密度動態放寬；使用者若要看更遠的店家，路徑為空狀態上的「改看全部店家」（無距離、不排序）。此上限值宜集中為單一可調整的設定，未來調整不需修改多處邏輯。
- 距離的呈現單位為公尺／公里，呈現精度屬實作細節，於 plan 階段確定。
- 座標取得的等待上限暫定為 10 秒，超過視為定位失敗。此數值於 plan 階段可依實測調整。
- 「全部店家清單」在無座標時的排列順序採穩定且可預期的順序（例如店名或建立時間），不做距離排序；具體排序欄位屬實作細節。

**資料與範圍**

- 店家／餐點資料表的 DDL 與 model **由第三輪（管理員後台）建立**——他們負責寫入，本輪只讀，由寫入方持有 schema 是正確的歸屬。本輪已刪除自己的 migration，並保留與其相同組織方式的 model 鏡像供合併前的本機驗證使用。本輪依賴的介面是 `from app.db.models import Store, MenuItem`，第三輪已保證其穩定。
- 座標為選填欄位，且以資料庫 CHECK 約束保證緯度與經度「同時有值或同時為 NULL」，不會出現只有其一的資料。本輪的讀取端仍保留防禦性檢查（成本為零），但不需為此設計使用者可見的錯誤情境。
- 地址為必填欄位（NOT NULL）。本輪的讀取端型別仍維持可空以保持寬容——行為不變且成本為零，見 [research.md](./research.md) 的說明。
- 餐點營養欄位可能為 0（店家登錄該營養素為零），此為有效數值而非缺值。
- 本輪不提供店家搜尋、名稱篩選、營業時間、店家照片、評分或分類標籤等欄位與功能——共用契約未定義這些欄位，本輪不得自行增補。
- 本輪不提供「將店家餐點一鍵記入飲食紀錄」的功能。餐點瀏覽為唯讀資訊呈現，與第一輪的拍照記帳流程不互相串接。
- 餐點的營養數值單位沿用共用契約的欄位命名語意（calories 為大卡，protein_g／carbs_g／fat_g 為公克），且為「每份餐點」的數值而非每 100 公克；本輪不提供份量調整。
- 測試資料的座標分布以可驗證排序為原則設定，不代表真實店家位置；正式資料由第三輪後台寫入。

**環境與既有實作**

- 第一輪的使用者資料表、LINE Login 驗證邏輯與後端 API 架構已完成且穩定，本輪直接沿用而不修改。
- 客戶端不保留離線資料；店家與餐點資料每次即時取自後端（依專案憲章「單一後端，多客戶端即時呼叫」）。
- 使用者的定位座標屬個人資料，其蒐集與利用需符合個人資料保護相關法規要求；本輪不保存座標，僅作單次查詢輸入。
