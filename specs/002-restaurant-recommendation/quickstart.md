# Quickstart: 推薦餐廳（第二輪）

**Date**: 2026-08-04 | **Plan**: [plan.md](./plan.md) | **Contracts**: [contracts/openapi.yaml](./contracts/openapi.yaml)

本文件是**驗證指南**：如何把本輪功能跑起來，以及用哪些情境確認它符合規格。
實作細節屬 `tasks.md` 與實作階段，此處不重複。

## 前置條件

第一輪環境已可運作（見 [specs/001-diet-log-mvp/quickstart.md](../001-diet-log-mvp/quickstart.md)）。本輪**不新增**任何服務、套件或環境變數依賴，只多兩個可選的調校參數：

| 變數 | 預設 | 說明 |
|---|---|---|
| `NEARBY_RADIUS_KM` | `5.0` | 附近店家的半徑上限（spec FR-020）。暫定值，實地測試後可調（OQ-7） |
| `NEARBY_LIMIT` | `10` | 附近店家的回傳筆數上限（spec FR-014） |

> 定位不需要任何金鑰或第三方服務——座標由瀏覽器 `navigator.geolocation` 提供。

## 啟動與載入測試資料

```bash
# 1. 資料庫遷移（建立 stores 與 menu_items）
cd backend
alembic upgrade head

# 2. 載入測試店家／餐點（FR-033）
#    可重複執行：主鍵由店名以 uuid5 推導，重跑為更新而非重複插入
python -m app.scripts.seed_stores

# 3. 後端
uvicorn app.main:app --reload

# 4. 前端
cd ../frontend && npm run dev
```

清除測試資料（正式資料不受影響——測試店家一律以 `[測試]` 前綴命名）：

```bash
python -m app.scripts.seed_stores --purge
```

### 測試資料的組成

以**台北車站 `25.0478, 121.5170`** 為參考點。用瀏覽器 DevTools 的 Sensors 面板把定位覆寫成這個座標，即可重現下列全部情境。

| 分組 | 筆數 | 用途 |
|---|---|---|
| 參考點 5 公里內 | 12 | 驗證「取最近 10 家」的截斷與排序（>10 筆才驗得到） |
| 參考點 5 公里外（淡水、基隆） | 2 | 驗證半徑排除與「改看全部店家」 |
| 座標留空（後台允許的常態資料） | 1 | 驗證排除於距離排序、但出現在全部清單（FR-018） |
| **同名不同址的連鎖分店** | 2 | 驗證以 id 識別、以地址區分，不去重（FR-016a） |
| 餐點 ≥ 8 筆的店家 | 1 | 驗證清單捲動 |
| 餐點 0 筆的店家 | 1 | 驗證餐點空狀態（FR-024） |
| 四欄營養皆 NULL 的餐點 | ≥1 | 驗證顯示「無資料」（FR-025 前半） |
| **營養數值確實為 0 的餐點** | ≥1 | 驗證顯示 `0` 而非「無資料」（FR-025 後半） |
| 同店家內同名的兩筆餐點 | 2 | 驗證不去重 |

## 驗證情境

每一項都可獨立執行。標示 ★ 者是本輪最容易做錯、且錯了不會立刻看出來的項目。

### V1 — 定位授權後看到最近的店家（US1、FR-005、FR-014、FR-016）

1. DevTools → Sensors → Location 設為台北車站座標。
2. 以 LIFF 環境進入服務（本機以 `NEXT_PUBLIC_LIFF_ID` 模擬，或用 E2E 測試的環境注入）。
3. 底部導覽點「找餐廳」。

**預期**：出現定位權限請求 → 允許後顯示店家清單，**恰 10 筆**（5 公里內有 12 家），每筆顯示店名、地址、距離，距離由近至遠。

★ **常見錯誤**：出現 12 筆（半徑過濾放在取前 10 之後，或漏了 `LIMIT`）；出現 11 筆（把座標留空那筆算成距離 0 排在第一）。

確認**座標留空的那家店不在清單中**（FR-018）——它會在 V4 的全部清單中出現。

### V2 — 半徑邊界與筆數不足（FR-020）

把 Sensors 座標改為**淡水**（`25.1677, 121.4406`），重新載入頁面。

**預期**：清單只出現淡水附近 5 公里內的店家（測試資料中為 1 家），**不會**以台北車站的店家補足到 10 筆。

★ 這一項驗的是 FR-020 明文禁止的「以超出範圍的店家補足名額」。

### V3 — 附近查無店家 vs 尚無店家資料（FR-019、SC-004、R-05）

1. 把 Sensors 座標設為**高雄**（`22.6273, 120.3014`），重新載入。
   **預期**：「附近查無店家」空狀態 ＋「改看全部店家」按鈕；點擊後看到全部店家清單，**不顯示距離**。
2. 清空資料庫店家（`--purge`）後重新載入。
   **預期**：「目前尚無店家資料」，**不出現**「改看全部店家」按鈕。

★ 兩種空狀態必須是不同文案與不同操作。若只看 `stores: []` 而未看 `total_store_count`，兩者會長得一模一樣——第二種情況點「改看全部店家」只會導向另一個空清單。

### V4 — 拒絕授權（US3、FR-008）

瀏覽器設定中封鎖該站的位置權限，重新進入「找餐廳」。

**預期**：顯示「已拒絕定位權限」說明 ＋ 重新開啟權限的指引，**同時**呈現全部店家清單（不排序、不顯示距離）。清單可正常點選進入餐點頁。

★ **座標留空的那家店必須出現在這份清單中**（FR-018）——它在 V1 的距離排序清單中被排除，但在這條不排序的路徑上是正常資料。這是雙方明確議定的行為。

### V5 — 定位服務失敗，與拒絕授權分屬不同畫面（FR-007、FR-009、SC-005）★

權限允許，但 DevTools → Sensors → Location 設為 **"Location unavailable"**，重新進入。

**預期**：

- 文案指向**裝置定位設定／訊號問題**，與 V4 的權限文案**明顯不同**。
- 出現「重試定位」按鈕（V4 沒有）。
- 同樣呈現全部店家清單。
- 把 Sensors 改回台北車站座標後點「重試定位」→ 畫面切換為依距離排序的清單，**不需重新整理頁面**（FR-011）。

★ 這是本輪最容易被合併成單一「定位失敗」畫面的地方。規格明文要求兩者分開（FR-007），驗收時必須兩種都跑。

### V6 — 逾時（FR-010）

以 DevTools 網路節流或在測試中 stub `getCurrentPosition` 使其永不回呼。

**預期**：10 秒後進入與 V5 相同的「定位服務失敗」處理，**不會**無限期停留在載入狀態。

### V7 — 餐點瀏覽、缺值與零值（US2、FR-023、FR-025）★

在清單點選餐點數 ≥ 8 的店家。

**預期**：顯示店名與餐點清單，每項含名稱、熱量與蛋白質／碳水／脂肪，且**兩個方向都要對**：

| 資料 | 必須顯示 | 顯示成這樣就不通過 |
|---|---|---|
| 四欄皆 `null` 的那筆 | 「無資料」 | `0` 或 `0 g`（會被讀成「不含該營養素」） |
| 營養值確實為 `0` 的那筆 | `0` | 「無資料」（抹掉店家明確登錄的資訊） |

★ 這是本輪最容易寫錯的一行程式：`0` 是 falsy，`value or '無資料'`、`value ? fmt(value) : '無資料'`、`{value && ...}` 都會把 0 誤顯示為「無資料」。必須以 `=== null` / `is None` 明確判斷。第二列的測試資料存在的唯一理由就是抓這個。

同時確認同店家內的兩筆同名餐點**各自列出**，未被去重。

### V7b — 同名連鎖分店（FR-016a）★

在清單中找到兩家同名的測試分店。

**預期**：兩家**各自列出**（未合併、未去重），以地址區分；分別點入後各自顯示自己的餐點，不會互串。

★ 若清單以店名作為 React key，兩筆同名店家會觸發 key 重複並可能渲染錯亂。識別一律用 `id`。

### V8 — 餐點空狀態與返回行為（FR-024、FR-026、US2-4）

1. 進入餐點數為 0 的店家 → **預期**：「此店家尚未提供餐點資訊」＋返回操作，非空白畫面。
2. 自任一餐點頁按返回 → **預期**：回到清單且**排序與內容不變**，且**不再彈出定位權限請求**。

★ 第 2 點驗的是 R-10 的 query cache 設計。若座標放在元件 state，返回時會重新請求權限。

### V9 — 入口限定（FR-001〜FR-003、SC-006）★

以**一般瀏覽器**（非 LIFF）登入。

**預期**：

- 底部導覽**沒有**「找餐廳」分頁。
- 直接手打 `/restaurants` 網址 → 顯示「此功能僅於 LINE 內提供」與返回操作，**不是**白畫面或錯誤畫面。
- 第一輪的儀表板、拍照、趨勢、個人設定全部正常。

★ 導覽列在環境判定完成前不得短暫閃現該分頁（research.md R-03）。

### V10 — 唯讀範圍（FR-029）★

```bash
curl -X POST http://localhost:8000/api/v1/stores -H "Authorization: Bearer <token>"
curl -X DELETE http://localhost:8000/api/v1/stores/<id> -H "Authorization: Bearer <token>"
```

**預期**：兩者皆 404／405，因為**這些端點不存在**。

同時檢查 `http://localhost:8000/openapi.json`：`/stores` 相關路徑下**只能有 `get`**。寫入端點屬第三輪，本輪不預先實作也不預留（brief 明訂）。

### V11 — 兩套營養資料互不干擾（FR-030、FR-031、憲章原則 V）★

1. 在 `food_nutrition_references` 中找一筆食物（例如「排骨便當」），記下其每 100 公克熱量。
2. 直接改資料庫把該筆熱量改成明顯不同的值。
3. 重新載入同名餐點的店家餐點頁。

**預期**：畫面數值**完全不變**——店家餐點營養值來自 `menu_items`，與通用對照表無任何連動。

反向亦然：改 `menu_items` 的數值不影響拍照辨識的換算結果。

### V12 — 未登入與不存在的店家（FR-027、沿用第一輪行為）

- 清除 token 後呼叫 `GET /stores` → 401，前端導回登入並在登入後回到原頁。
- 以不存在的 UUID 進入餐點頁 → 顯示「此店家已不存在」與返回清單的操作，非無法離開的錯誤畫面。

### V13 — 視覺一致性與免責（FR-036、FR-037）

切換深色模式瀏覽清單與餐點頁。

**預期**：色彩、字體、圓角與第一輪各頁一致；餐點營養數值附近有「估算參考值」的說明文字。

## 合併回 main 前的人工確認 ⚠️

本輪與第三輪（管理員後台）在不同分支上共用同一張資料表。依 2026-08-04 交接說明，**兩張表由先合併回 `main` 的一方建立，另一方沿用**，誰先建立需互相知會。

建表前（不是合併前——先建表的一方等於為雙方定案）：

1. **主鍵型別**（OQ-1，**未定案**）——UUID 與 BIGSERIAL 的差異無法靠改名解決，需一方重建資料表。交接說明未涵蓋此項。
2. **營養欄位 nullability**（OQ-2b，**未定案**）——本輪要求四欄 nullable（FR-025「無資料」的前提）。交接確認了「0 顯示為 0」，但未言明 NULL 可否寫入；若設 NOT NULL，「無資料」狀態將永不出現。

合併前：

3. **Alembic 雙 head**——若知會前雙方都已產生 migration，兩個 revision 會同時以 `0001` 為 parent。保留先合併一方的，後者刪除自己的並核對 model。
4. **語意約定是否已進入契約檔案**——契約檔案（已於 2026-08-04 同步欄位）只列欄位名稱；「座標選填」「名稱不唯一」「實刪除＋CASCADE」「0 為有效數值」等議定行為目前僅存在於交接說明中。建議合併時一併補入，否則日後只讀契約檔案的人看不到這些。
