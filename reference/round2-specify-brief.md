這是本產品第二輪 spec，對應 reference/Caluli_AI拍照飲食紀錄助手產品企劃書.txt
的 2.7「推薦餐廳（新功能模組）」，只處理本輪範圍內的功能，管理員角色與後台
（由另一位開發者在 feature/round3-admin 分支平行進行）、Flutter 客戶端不在
本輪範圍。

第一輪（拍照辨識、熱量追蹤、LINE Login、趨勢圖表）已經完成 implement，
程式碼與資料表已實際存在於本專案中。本輪請先閱讀現有專案結構，沿用第一輪
已建立的使用者資料表、LINE Login 驗證邏輯與後端 API 架構，不要重新設計
或修改這些既有部分。

【資料表結構 — 共用契約】
店家/餐點的資料表結構請完全依照 reference/shared-schema-store-menu.md 的
定義執行，不要自行增減欄位或修改欄位名稱，因為這張表由另一位開發者的
第三輪 feature（管理員後台）共用，對方會在同一張表上做 CRUD 介面，
雙方的分支之後會合併回同一個 main，欄位對不上會導致合併衝突。

【本輪功能範圍】
- 開放使用者讀取店家與餐點資料（唯讀，本輪不做新增/修改/刪除介面，
  那是第三輪的範圍，本輪的 API 只需要提供 GET 查詢）
- 定位權限：前端向使用者請求「目前位置」權限，比照第一輪相機權限的請求
  模式；使用者拒絕授權時的替代方案為退回顯示全部店家清單，不特別排序
- 座標與距離排序：後端依使用者目前座標，從店家清單計算距離、排序並
  回傳最近 10 家；店家數量不大，計算單純，不需要導入額外的地理資料庫工具
- 店家內餐點瀏覽：使用者點選特定店家後，可瀏覽該店餐點清單，每項餐點
  顯示熱量與三大營養素
- 使用範圍限定：整個推薦餐廳模組（定位、店家清單、餐點瀏覽）僅於 LIFF
  入口提供，一般網頁、iOS App、Android App 三個入口不實作此功能

【資料模型重要提醒】
「店家／餐點／營養數值」這組資料，與第一輪拍照辨識所使用的通用食物營養
對照表，是兩套完全獨立的資料，不要嘗試複用、合併或建立關聯：
- 第一輪的表：AI 辨識用的通用食物營養值
- 本輪的表：特定店家、特定餐點的營養值（即使食物名稱相同，也是這家店
  自己登錄的獨立數值，不查詢或連動第一輪的通用對照表）

【明確排除】
- 店家/餐點的新增、編輯、刪除介面（屬於第三輪管理員後台，本輪只需要
  提供唯讀查詢 API，資料的寫入由第三輪的後台介面負責）
- 一般網頁、iOS、Android 三個入口不需要實作推薦餐廳的任何畫面
- 合作店家點餐流程、訂單系統 API 串接（不在任何一輪範圍內）

【資料如何先有內容可供測試】
本輪 implement 階段可能需要一些測試用的店家/餐點假資料才能驗證定位排序、
清單顯示等功能是否正常，因為第三輪的新增介面可能還沒做完，本輪請直接
用資料庫 seed script 或 migration 附帶幾筆測試資料，不要等待第三輪完成
才能測試自己的功能。

【錯誤與邊界情境，請在 spec 中一併補上驗收標準】
- 定位權限被拒絕時的畫面與行為（已在上方說明）
- 附近查無店家（清單為空、或距離過遠）時的空狀態畫面
- 定位服務本身失敗（裝置定位功能關閉、GPS 訊號問題）與拒絕授權是不同
  情境，請分開處理並各自定義對應畫面

【視覺與互動參考】
延續第一輪已確立的視覺風格（色彩、字體、圓角、深色模式）維持一致性，
不需要另外對照 reference/prototype/caiuli.html（該 prototype 沒有涵蓋
店家清單/餐點瀏覽畫面），版面配置請依現有頁面風格延伸設計。
