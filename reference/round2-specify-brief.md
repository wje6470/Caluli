這是本產品第二輪 spec，對應 reference/Caluli_AI拍照飲食紀錄助手產品企劃書.txt
的 2.7「推薦餐廳（新功能模組）」，只處理本輪範圍內的功能，管理員角色與後台、
Flutter 客戶端屬於後續獨立的 spec 輪次，本輪不要涉及。

第一輪（拍照辨識、熱量追蹤、LINE Login、趨勢圖表）已經完成 implement，
程式碼與資料表已實際存在於本專案中。本輪請先閱讀現有專案結構，沿用第一輪
已建立的使用者資料表、LINE Login 驗證邏輯與後端 API 架構，不要重新設計
或修改這些既有部分。

【本輪功能範圍】
- 開放使用者讀取店家與餐點資料（唯讀，使用者無法新增/修改/刪除，管理端
  的維護功能屬於第三輪，本輪不做）
- 定位權限：前端向使用者請求「目前位置」權限，比照第一輪相機權限的請求
  模式；使用者拒絕授權時的替代方案為退回顯示全部店家清單，不特別排序
- 座標與距離排序：店家資料需具備經緯度，後端依使用者目前座標計算距離、
  排序並回傳最近 10 家；店家數量不大，計算單純，不需要導入額外的地理
  資料庫工具
- 店家內餐點瀏覽：使用者點選特定店家後，可瀏覽該店餐點清單，每項餐點
  顯示熱量與三大營養素
- 使用範圍限定：整個推薦餐廳模組（定位、店家清單、餐點瀏覽）僅於 LIFF
  入口提供，一般網頁、iOS App、Android App 三個入口不實作此功能，請在
  前端加上對應的入口判斷邏輯

【資料模型重要提醒】
「店家／餐點／營養數值」這組資料，與第一輪拍照辨識所使用的通用食物營養
對照表，是兩套完全獨立的資料，概念不同，請建立獨立的資料表，不要嘗試
複用、合併或與第一輪的營養資料表建立關聯：
- 第一輪的表：AI 辨識用的通用食物營養值（例如「滷肉飯」這個食物本身的
  營養值）
- 本輪的表：特定店家、特定餐點的營養值（例如「某店家的招牌滷肉飯」，
  即使食物名稱相同，也是這家店自己登錄的獨立數值，不會去查詢或連動
  第一輪的通用對照表）

【店家座標補充方式（待確認事項，先假設一種預設方案，並在 plan 中標註）】
店家資料需要補上經緯度，取得方式有兩種可能：由系統在建立店家資料時自動
將地址轉換為座標（需要串接地理編碼服務），或由管理員直接輸入座標。本輪
先假設「先支援手動輸入座標」作為 MVP 設計，地址自動轉換列為待確認的
未來擴充項目，不是本輪必須完成的範圍（店家資料的建立介面本身也不在本輪，
屬於第三輪管理後台的範圍，本輪只需要設計資料表結構能存放座標）。

【明確排除】
- 店家/餐點的新增、編輯、刪除介面（屬於第三輪管理員後台）
- 一般網頁、iOS、Android 三個入口不需要實作推薦餐廳的任何畫面
- 合作店家點餐流程、訂單系統 API 串接（企劃書中已列為 Out of Scope，
  不在任何一輪範圍內）

【視覺與互動參考】
可延續第一輪已經確立的視覺風格（色彩、字體、圓角、深色模式）維持一致性，
不需要另外重新對照 reference/prototype/caiuli.html，因為那份 prototype
主要呈現的是拍照辨識與儀表板頁面，沒有涵蓋店家清單/餐點瀏覽的畫面，
這部分版面配置請你依現有頁面風格延伸設計。

【錯誤與邊界情境，請在 spec 中一併補上驗收標準】
- 定位權限被拒絕時的畫面與行為（已在上方說明）
- 附近查無店家（例如店家清單為空、或距離過遠）時的空狀態畫面
- 定位服務本身失敗（例如裝置定位功能關閉、GPS 訊號問題）與拒絕授權是
  不同情境，請分開處理並各自定義對應畫面
