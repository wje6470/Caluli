【技術棧鎖定】 沿用第一輪已確立的技術棧：前端 Next.js，後端 FastAPI，資料庫 PostgreSQL。 本輪只新增功能，不更換任何既有技術選型。 【資料表結構 — 共用契約，優先於本輪任何自行推導的設計】 店家/餐點資料表結構請完全依照 reference/shared-schema-store-menu.md 執行， plan.md 中規劃資料庫 migration 時，請直接引用該檔案定義的欄位，不要自行 增減或重新命名。若發現這份契約不足以支撐後台的寫入需求（例如需要一個 「是否上架顯示」的欄位），請在 plan.md 中列為 open question 提出， 不要自行加欄位後直接實作，因為第二輪的分支同時在讀取這張表，欄位變動 需要雙方協調。 【權限檢查層設計】 請具體規劃「僅管理員可通過」的權限檢查機制，例如 FastAPI 的 dependency injection 方式，在管理員專屬的路由群組上統一套用，與一般 使用者可呼叫的 API 路由完全分開掛載（例如管理員 API 統一掛在 /api/admin/* 前綴下）。請說明管理員身分的判斷方式：是在使用者資料表 新增一個 role 或 is_admin 欄位，登入驗證時一併帶出這個資訊，並在 權限檢查層讀取這個欄位判斷。 【管理員指派的實作方式】 由於管理員身分是後端指定、不開放自行申請，請在 plan.md 中列出你打算 怎麼實作「指定管理員」這件事的技術方案（例如：直接在資料庫手動更新 使用者的 role 欄位，或提供一支只有特定金鑰能呼叫的內部 API），並說明 這個方案的安全性考量（例如避免一般使用者能透過某種方式偽造請求把自己 變成管理員）。 【CRUD 介面技術決策】 後台介面優先度低、以精簡快速為原則，plan 階段可以決定用最簡單可行的 方式呈現（例如簡單的表格列表 + 表單彈窗，不需要複雜的元件庫或客製化 視覺設計），這不是需要花時間精心設計的部分，請把重點放在功能正確性 （新增/編輯/刪除是否正確寫入資料庫）而非視覺呈現。 【邊界情境的技術處理】 - 座標欄位請規劃為選填，若未填座標，plan.md 中請說明資料庫層如何允許 空值（nullable），並註明第二輪的距離排序功能在遇到座標為空的店家時 應如何處理（不納入排序結果，或排在清單最後 — 這部分屬於功能決策， 若 spec.md 已經定義請直接依循，若沒有請在 plan.md 中列為 open question） - 刪除店家時的 cascade 行為，請在資料庫 migration 中明確設定外鍵的 ON DELETE 規則（cascade 或 restrict），並說明選擇理由 【與第二輪分支的合併考量】 本輪與第二輪目前在不同的 git 分支平行開發，共用同一張資料表但操作方向 不同（本輪寫、第二輪讀）。請在 plan.md 中提醒：資料庫 migration 檔案 若由本輪先建立，之後與第二輪分支合併時可能需要協調 migration 順序或 合併衝突，這點列為合併前需要人工確認的事項，不需要 agent 現在處理， 只需要在 plan.md 中記錄這個風險即可。
