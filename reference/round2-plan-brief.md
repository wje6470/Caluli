【技術棧鎖定】
沿用第一輪已確立的技術棧：前端 Next.js（LIFF 容器），後端 FastAPI，
資料庫 PostgreSQL。本輪只新增功能，不更換任何既有技術選型。

【資料表結構 — 共用契約，優先於本輪任何自行推導的設計】
店家/餐點資料表結構請完全依照 reference/shared-schema-store-menu.md 執行，
plan.md 中規劃資料庫 migration 時，請直接引用該檔案定義的欄位，不要自行
增減或重新命名。若 plan 階段發現這份契約有不足以支撐本輪功能的地方
（例如缺少某個查詢必要的欄位），請在 plan.md 中列為 open question 提出，
不要自行加欄位後直接實作，因為這張表由另一位開發者的分支同時在寫入。

【距離排序的技術決策】
本輪不需要導入 PostGIS 或其他地理資料庫擴充套件，店家數量不大，直接在
應用層（或用簡單的 SQL 公式，如 Haversine 公式）計算使用者座標與各店家
座標的距離，取最近 10 家即可。請在 plan.md 中明確寫出用哪一種計算方式
（應用層迴圈計算 vs 資料庫層 SQL 計算），並簡要說明取捨。

【定位權限串接】
前端定位權限請求方式請比照第一輪相機權限的既有實作模式（如果第一輪有
建立可重用的權限請求元件或流程，本輪直接沿用；如果沒有，請說明本輪
會如何實作，並評估未來能否讓第一輪的相機權限與本輪的定位權限共用同一套
權限請求/被拒絕處理的 UI 元件）。

【本輪 API 只做讀取】
本輪後端 API 只需要提供 GET 查詢端點（店家清單、依距離排序、店家內
餐點清單），不需要新增/編輯/刪除的寫入端點，寫入端點由第三輪
（管理員後台）負責，本輪不要預先實作或預留這些端點，避免與第三輪重複
或衝突。

【測試資料】
implement 階段需要一些店家/餐點測試資料才能驗證距離排序、清單顯示等
功能，請規劃一個 seed script 或 migration 附帶測試資料（可以是台灣任意
幾個座標點的假店家），不需要等待第三輪的後台介面完成才能測試。

【本輪不處理】
座標的自動地理編碼（地址轉座標）不在本輪範圍，本輪先假設座標由後台
（第三輪）手動輸入即可存在資料庫中，本輪只負責讀取既有座標做排序運算。

【與第三輪分支的合併考量】
本輪與第三輪目前在不同的 git 分支平行開發，共用同一張資料表但操作方向
不同（本輪讀、第三輪寫）。請在 plan.md 中提醒：資料庫 migration 檔案
若由本輪先建立，之後與第三輪分支合併時可能需要協調 migration 順序或
合併衝突，這點列為合併前需要人工確認的事項，不需要 agent 現在處理，
只需要在 plan.md 中記錄這個風險即可。
