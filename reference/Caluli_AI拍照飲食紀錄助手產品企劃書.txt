一、產品概述

1.1 產品願景

現代人普遍希望能掌握每日飲食攝取狀況以利體重管理與健康維護，但傳統飲食紀錄工具（如手動搜尋品項、查詢熱量表）操作繁瑣，容易導致使用者中斷紀錄習慣。

此外，市面上現有的飲食紀錄產品多數集中於歐美食品資料庫，對亞洲在地飲食（如台式便當、夜市小吃、中式熱炒等）的辨識與熱量估算精準度顯著不足，無法滿足在地使用者的實際需求。

本專案旨在打造一款專注於「亞洲飲食」的健康管理服務，讓使用者只需拍一張照片即可掌握攝取熱量與營養素，大幅提高亞洲食品與複雜菜餚的分析精準度。產品以
LINE Mini App（LIFF）作為主要入口，維持 Web App
架構的開發效率，使用者無需另外下載 App，即可直接於 LINE 完成登入、AI
飲食辨識、飲食紀錄與健康數據查詢，兼具低門檻使用體驗與 LINE
生態系（好友關係、官方帳號、訊息推播）的導流與經營優勢。

1.2 產品階段定位

現行產品（本階段開發）：LINE Mini App（LIFF）健康管理服務（MVP）

-   產品入口：維持 Web App 架構之開發效率，前端同時支援 LINE LIFF
      與一般瀏覽器兩種執行環境；使用者可於 LINE 內開啟 LIFF
      頁面，或直接以一般瀏覽器造訪網頁版，完成登入、AI
      飲食辨識、飲食紀錄、健康數據查詢及店家資訊瀏覽。登入流程須同時支援兩種進入方式，不可假設一定執行於
      LIFF context 內。

-   個人基本資訊設定：紀錄與管理年齡、身高、體重及每日活動量。

-   熱量與目標管理：計算並即時顯示每日建議熱量、已攝取熱量及剩餘可用熱量。

-   當日飲食紀錄：支援多元上傳方式，點選後可自由選擇「使用相機即時拍照」或「從手機相簿上傳」餐點照片，系統自動辨識食物種類、估算份量並計算熱量與三大營養素（蛋白質、碳水、脂肪），使用者可手動修正辨識結果。

-   健康數據趨勢圖表：提供熱量攝取的長期趨勢圖表分析。

本次專案暫不包含範圍（Out of Scope）：

-   AI
      健身指導機器人：涉及複雜對話與動態運動處方，評估列為未來擴充項目。

-   穿戴式裝置（如 Apple
      Watch/Garmin）數據同步：專案期程考量，暫不進行第三方硬體串接。

-   合作店家點餐流程與訂單／會員系統 API
      串接：需仰賴合作店家提供資料介接，暫不列入本階段開發範圍。

-   其餘配套功能待後續補充，包含但不限於社群分享、多人挑戰賽、每日飲水量紀錄等。

-   不提供醫療級營養診斷或治療建議：本產品僅做熱量／營養素估算參考，不做疾病、過敏、處方等醫療判斷。

1.3 目標使用者

-   想更精準掌握每日飲食攝取的使用者

-   忙碌上班族，希望用最少操作時間完成飲食紀錄

-   有體重管理／減脂增肌需求，但尚無穩定記帳習慣的使用者

-   習慣使用 LINE、不希望額外下載新 App 的使用者，可透過 LINE
      好友或官方帳號快速上手

二、現行產品：LINE Mini App 健康管理服務（MVP）

2.1 核心功能：拍照分析食物熱量

使用者於 LINE 內開啟 LIFF
頁面，拍攝餐點照片後，系統自動辨識食物種類、估算份量並計算熱量與三大營養素（蛋白質、碳水、脂肪），使用者可手動修正辨識結果。

實作方式：採用 YOLO
物件偵測模型，偵測餐點照片中的食物品項與所在位置，再串接 Hugging Face
平台之食物分類／份量估算模型，輸出食物清單、估計份量、熱量與營養素，並以結構化
JSON 格式回傳前端顯示。

2.2 配套小功能（MVP核心與延伸項目）

為確保 MVP 產品體驗完整，本階段規劃以下配套模組：

-   個人基本資訊管理：設定年齡、身高、體重與活動量等級，作為系統計算
      BMR/TDEE 之基準。

-   每日熱量目標追蹤：儀表板動態顯示「每日建議熱量－已攝取熱量＝剩餘可用熱量」。

-   飲食紀錄：整合拍照辨識、上傳檔案、手動新增與修改飲食與營養資訊。

-   健康趨勢圖表：以折線圖／柱狀圖呈現每日熱量（營養）攝取變化。

-   身分登入：系統統一採用 LINE 快速登入（LINE Login／OAuth
      2.0）作為唯一登入方式，四個入口皆可完成登入，詳細規劃請見
      2.4「身分與登入架構」。

2.3 主要使用者流程（User Flow）

使用者於 LINE 好友或官方帳號選單點擊入口 ➔ 開啟 LIFF（LINE 內建瀏覽器）
➔ 透過 LINE Login 自動完成身分驗證
➔（首次使用）填寫個人基本資訊（年齡、身高、體重、活動量） ➔
系統自動計算每日建議熱量（TDEE/BMR） ➔ 進入主儀表板（查看今日剩餘熱量）
➔ 點擊「拍照記帳」 ➔ 開啟相機拍照／上傳相簿 ➔ AI 分析中（顯示 Loading
狀態） ➔ 確認／手動修正辨識結果（食物名稱、份量、熱量） ➔ 儲存紀錄 ➔
返回儀表板（熱量與圖表即時更新）

2.4 身分與登入架構

系統統一採用 LINE 快速登入（LINE Login／OAuth
2.0）作為唯一登入方式，不開放 Email
帳密自行註冊；不同入口依其執行環境採用對應的串接方式完成登入。

四個入口皆採 LINE 登入，串接方式各不相同

-   LIFF：沿用原本設計，自動帶入使用者 LINE 身分，使用者無感完成登入。

-   一般網頁（LIFF 以外）：改走 LINE 官方網頁版 OAuth
      登入流程，使用者需主動點擊「使用 LINE 登入」。

-   iOS／Android（Flutter）：整合 LINE 原生 SDK，裝置上已安裝 LINE App
      則直接跳轉授權，未安裝則退回網頁版 OAuth 流程。

-   後端驗證邏輯維持共用一套，不因入口不同而分岔。

前端不再限定 LIFF

-   服務前端不再限定只能在 LIFF 裡開啟，一般瀏覽器可直接使用。

-   需具備「目前是否執行於 LIFF 環境」之判斷能力：是則呼叫 LIFF
      相關功能；否則導向一般網頁 LINE OAuth 登入畫面，不可硬呼叫僅 LIFF
      才有的功能而導致錯誤。

2.5 角色與權限

管理員角色

-   使用者新增「角色」概念，區分一般使用者與管理員，不再假設所有使用者皆為同一種身分。

-   管理員角色獨立於一般使用者，其權限與消費者端完全分開；管理員登入方式與一般使用者相同，皆採
      LINE 快速登入，僅由後端將特定 LINE
      使用者指派為管理員角色以區分權限，不另外開放帳密登入。

-   須建立僅管理員可通過的權限檢查層，與一般使用者可呼叫之 API
      完全隔開，避免一般使用者的登入狀態誤觸後台功能。

後台管理能力

-   提供管理員專用介面：新增／編輯／刪除店家（名稱、地址、地理座標等）、新增／編輯／刪除店家底下餐點（名稱、熱量、蛋白質、碳水、脂肪）。

-   此介面服務對象為少數內部人員，體驗要求可低於主要產品，以精簡、快速完成為原則，不需額外投入打磨。

2.6 進入點結構

LINE 端不再是單一入口，改為透過 Rich Menu 分流至兩個獨立的 LIFF 頁面。

-   Rich Menu 分流：LINE
      官方帳號選單至少設定兩個按鈕，分別導向對應既有健康管理主頁面之
      LIFF 頁面，以及對應推薦餐廳模組之 LIFF 頁面。

-   技術實作方式待定：此兩個 LIFF
      頁面可以是同一前端專案下的不同路由，也可以是完全分開的兩組 LIFF
      設定，此點尚未定案，屬後續待確認之技術選項。

-   共用身分與服務：無論採何種實作方式，兩個入口皆共用同一組登入身分與後端服務。

2.7 推薦餐廳（新功能模組）

新增與現行拍照辨識／熱量追蹤功能平行的「推薦餐廳」功能模組，提供店家與餐點資料讀取，並依使用者位置提供最近店家查詢。

資料開放使用者讀取

-   店家／餐點資料原僅供管理員維護，現同時開放使用者端瀏覽查詢；使用者僅能讀取，無法修改。

定位與距離排序

-   前端需向使用者請求「目前位置」權限，比照現有相機權限之請求模式，若使用者拒絕授權則顯示預設熱門清單。

-   店家資料需補上經緯度：可於管理員新增店家時由系統自動將地址轉換為座標，或由管理員直接輸入座標。

-   後端依使用者目前座標，從店家清單計算距離、排序並取最近 10
      家；在店家數量不大的前提下，此運算單純，不需另外導入複雜的地理資料庫工具。

店家內餐點瀏覽

-   使用者點選特定店家後，可瀏覽該店餐點清單，每項餐點顯示熱量與三大營養素。

-   「店家／餐點／營養數值」這組資料與現行拍照辨識所使用的通用食物營養對照表為兩套完全獨立的資料，不共用同一份資料表：前者為特定店家、特定餐點之營養值，後者為
      AI 辨識用之通用食物營養值，概念不同，避免混用。

使用範圍限定 LIFF

-   整個推薦餐廳模組（定位、店家清單、餐點瀏覽）僅於 LIFF
      入口提供；一般網頁、iOS App、Android App 三個入口不實作此功能。

3.2 系統流程說明

① 使用者於 LINE 內開啟 LIFF 頁面，透過 LINE Login 完成身分驗證 → ②
於頁面內拍照或掃描條碼 → ③ FastAPI 後端接收請求 → ④ 依情況以 YOLO
模型偵測食物品項與位置，再呼叫 Hugging Face
食物分類／營養估算模型進行份量與熱量預估，或直接查詢條碼資料庫 → ⑤
解析回傳結構化結果（食物項目、份量、熱量、營養素）→ ⑥ 寫入 PostgreSQL
資料庫並回傳 LIFF 頁面顯示 → ⑦ 使用者可修正結果，修正後資料回存。

3.3 多平台架構

系統由單一前端架構，改為多客戶端共用同一後端服務之架構，涵蓋
LIFF、一般網頁、iOS App、Android App
四個客戶端，各端之使用者身分與資料需即時互通。

多客戶端共用同一後端

-   後端 API 須同時服務四種客戶端，認證邏輯不可假設請求必然來自
      LIFF，須改為不論憑證取得自哪個客戶端，只要驗證通過即予放行。

-   四個客戶端皆即時呼叫同一後端、不於本機保留離線資料，資料本身即維持一致，不需另外開發同步機制。

Flutter 客戶端

-   iOS 與 Android 採用 Flutter 開發，為完全獨立於現有網頁前端的新專案。

-   原規劃給網頁使用的主要頁面（引導同意頁、儀表板、拍照畫面、辨識結果確認、手動輸入、趨勢圖、設定頁）須於
      Flutter 端重新開發，為本次改動中工作量最大的一項。

-   Flutter 端串接 LINE 登入需改用 LINE 官方提供之原生 App
      SDK（iOS／Android 各自一套），裝置上已安裝 LINE App
      則直接跳轉授權，未安裝則退回網頁版 OAuth 流程。

-   Flutter
      端需實作相機與相簿存取，實作方式與網頁版不同，但功能（拍照、上傳照片）需對等。

發佈方式

-   iOS 與 Android 皆不透過 App Store／Google Play 正式上架審核。

-   改為於網頁提供下載按鈕，使用者可直接下載安裝檔自行安裝；此方式免去上架審核所需素材準備，但使用者安裝時可能需自行調整手機安全性設定，其中
      iOS 限制較 Android 嚴格（此限制目前評估暫不特別處理）。

代管服務而定，建議另外提供互動式試算工具比較不同部署方式與規模情境。未來若擴充合作店家餐點整合或
LINE
官方帳號推播訊息量提升，需另外評估對話、資料串接與訊息則數帶來的增量成本。

五、開發步驟規劃（飲食紀錄產品）

  -----------------------------------------------------------------------
  步驟                主要任務
  ------------------- ---------------------------------------------------
  Step 1：原型驗證    Figma 流程圖／UI 原型，內部測試核心體驗

  Step 2：MVP開發     網頁前端骨架（Next.js）＋ LINE LIFF SDK 整合與 LINE
                      Login ＋ FastAPI 後端＋資料庫建置＋拍照分析功能串接

  Step 3：配套功能    網頁、推薦店家、聯絡我們等小功能開發

  Step 4：內測與優化  種子使用者測試、成本與準確度校正、UI打磨

  Step 5：正式上線    LINE Mini App
                      飲食紀錄產品發布，蒐集使用者回饋作為未來擴充依據

六、風險與待辦事項

-   食物份量估算準確度有限，需透過使用者修正機制持續優化

-   YOLO 與 Hugging Face
      食物辨識模型需仰賴足量且具代表性的亞洲飲食標註資料集進行訓練與微調，資料蒐集與模型迭代需納入開發排程

-   YOLO／Hugging Face
      模型之運算資源與服務費用會隨使用者規模與拍照頻率成長，需持續監控主機負載並視情況調整模型部署與分流策略

-   健康／飲食相關內容需明確法律免責聲明，避免醫療建議疑慮

-   LIFF 於不同裝置（iOS／Android LINE App
      內建瀏覽器）之效能與相容性需事先測試

-   合作店家資料串接與 API
      介接複雜度較高，需依各合作店家系統能力逐一評估，屬未來擴充功能之前置風險

-   LINE 官方帳號訊息推播涉及訊息則數費用，需納入未來擴充階段之成本規劃

-   會員資料串接 LINE
      官方帳號涉及個資蒐集與利用，需符合個資法等相關法規要求

-   配套小功能尚待進一步盤點與優先順序排序
