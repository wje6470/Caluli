【店家/餐點資料表 — 第二輪與第三輪共用契約，兩邊都以此為準，不得自行更改欄位】

stores 表：
- id
- name（店家名稱）
- address（地址）
- latitude, longitude（經緯度）
- created_at, updated_at

menu_items 表：
- id
- store_id（外鍵，關聯 stores）
- name（餐點名稱）
- calories
- protein_g
- carbs_g
- fat_g
- created_at, updated_at


【欄位語意補充 — 2026-08-04 補充，非欄位增減，兩邊實作須一致】

以下三點原契約未載明，第三輪 spec 撰寫時發現雙方會各自解讀，經確認後定案。
欄位名稱與數量除上述 menu_items 補上時間戳外，未做任何其他變更。

1. latitude / longitude 可為空值（選填）
   - 允許只有名稱與地址、尚未設定座標的店家存在。
   - 兩者必須同時有值或同時為空，不會出現只有緯度或只有經度的資料
     （第三輪的寫入端負責攔截）。
   - 讀取端（第二輪）務必處理空值：未設定座標的店家不參與距離計算，
     且不出現在依距離排序的結果中；但在不排序的完整店家清單中要正常出現
     （對應第二輪「使用者拒絕定位授權 → 退回顯示全部店家、不特別排序」的路徑）。
   - 系統不驗證地址與座標是否一致，距離計算一律以座標為準，地址僅供顯示。

2. name 不具唯一性
   - stores.name 允許重複（連鎖分店以 address 區分）。
   - 同一店家底下的 menu_items.name 也允許重複，不強制唯一。
   - 不同店家底下的同名餐點各自獨立，修改其一不連動另一。

3. 刪除為實刪除，且店家連帶刪除其餐點
   - 契約不含 deleted_at / is_active 等欄位，刪除即資料自資料庫移除，不可還原。
   - 刪除店家時一併刪除其底下所有 menu_items，不會殘留無所屬店家的餐點。
   - 讀取端不需要（也不應該）加任何「排除已刪除」的過濾條件。
   - 若未來需要「店家暫時休業／暫停合作」的上下架能力，屆時新增 is_active
     欄位即可：新欄位預設為上架、既有資料全部視為上架，無資料遷移風險。
     此為經評估後的決定，非疏漏；在有明確營運需求前不提前加入。

【變更紀錄】

- 2026-08-04：menu_items 補上 created_at, updated_at，與 stores 一致。
  原因：原契約僅 stores 有時間戳，餐點無法得知建立與最後修改時間；此欄位
  若延後補上，既有資料的真實時間永遠無法回溯，故於實作前補齊。
  影響：第二輪讀取端無須配合修改（新增欄位、不影響既有查詢）；
  第三輪寫入端負責自動填入，不需管理員輸入。
- 2026-08-04：補上「欄位語意補充」三點（見上），未增減欄位。
