【本輪功能範圍】
- 個人基本資訊管理（年齡/身高/體重/活動量 → 計算 BMR/TDEE）
- 每日熱量目標追蹤儀表板
- 拍照/相簿上傳 → AI 辨識 → 使用者確認與手動修正 → 儲存紀錄
- 健康趨勢圖表
- LINE Login（本輪先做 LIFF + 一般網頁兩種入口，iOS/Android 留給 Flutter
  那一輪）
- 完整 User Flow：LINE 好友/官方帳號入口 → LIFF/OAuth 登入 → 首次填寫個人
  資訊 → 計算 TDEE/BMR → 主儀表板 → 拍照記帳 → AI 分析（Loading）→ 確認/
  修正結果 → 儲存 → 返回儀表板更新

【明確排除】
AI 健身指導機器人、穿戴裝置同步、合作店家訂單 API、社群分享／多人挑戰／
飲水紀錄、醫療級診斷建議 — 這些都不在本輪範圍。

【AI 辨識模型資訊 — 模型已訓練完成，本輪只需串接，不需訓練或優化】

模型分兩階段：
1. YOLO 偵測模型：輸入一張完整照片，輸出一個 list，列出照片中偵測到的
   每一樣食物（含位置）
2. Hugging Face 分類模型：輸入 YOLO 切出來的、只有單一食物的裁切小圖，
   輸出 Top-K 個可能的分類結果（依信心度排序）

重要限制：HF 分類模型無法偵測實際克數／份量，因此份量估算改用以下流程：

  照片
   → YOLO 切出每個食物
   → HF 分類模型判斷食物名稱（例如「滷肉飯」）
   → 查詢營養資料庫，取得該食物每 100g 的熱量/蛋白質/脂肪/碳水
   → 系統套用「預設份量」（例如滷肉飯預設 250g，由後端設定的合理估計值，
     非模型輸出）
   → 用預設份量算出初步結果並顯示給使用者，同時附上一個可調整的欄位/滑桿
   → 使用者依實際感受調整克數
   → 系統即時重新計算：每100g數值 × (使用者調整後克數 / 100)

請注意：這代表前端在「AI 辨識結果確認」畫面，除了顯示食物名稱/熱量/營養素
外，「份量」欄位必須是預設值 + 可即時互動調整的元件（滑桿或輸入框），
調整後畫面上的熱量與營養素數值要跟著即時重新計算，這是核心互動需求，
不是次要細節。

部署位置：模型服務會跟主程式部署在同一台伺服器上（非獨立的第三方
Hugging Face Inference Endpoint，也非跨網域呼叫），實作時後端可視為
內部服務呼叫。

呼叫方式：目前尚未確定是同步或非同步、也還沒有明確的回應時間預期，
請 spec 階段先假設「同步等待回應」作為預設設計，並在 plan 階段標註此為
待確認事項（open question），保留未來若改為非同步（如輪詢或 WebSocket）
時的彈性，不要把同步呼叫寫死成無法更改的架構決定。

錯誤回傳格式（已確認）：
{
  "items": [],
  "message": "沒有偵測到食物，請換一張再試試"
}
當 items 為空陣列時，前端需顯示對應的錯誤/引導畫面（例如提示使用者換一張
照片重拍），而不是嘗試渲染空的辨識結果列表。

前端串接需求：呼叫辨識服務期間需顯示 Loading 狀態；除了上述「沒偵測到
食物」的已知錯誤格式外，也請一併規劃網路逾時、伺服器錯誤等未列在
model-spec.md 裡、但實際上線後可能發生的情境，並定義對應的錯誤畫面與
重試機制。
