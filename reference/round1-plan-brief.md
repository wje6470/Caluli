【技術棧鎖定】
前端：Next.js，需同時支援 LIFF 容器內執行與一般瀏覽器兩種環境，需具備
「目前是否執行於 LIFF 環境」的判斷邏輯（例如透過 LIFF SDK 的 isInClient()
或環境變數判斷），依判斷結果分流登入方式。
後端：FastAPI
資料庫：PostgreSQL
登入：LINE Login（LIFF 走自動帶入、一般網頁走 LINE 官方網頁版 OAuth），
後端驗證邏輯共用一套，不因入口分岔。

【視覺與互動參考】
UI 風格請對照 reference/prototype/caiuli.html：
- 色彩、字體、圓角、卡片陰影、深色模式（dark class 切換）
- 底部導覽列的分頁切換節奏、Modal 開合動畫
但元件結構請依 Next.js 專案慣例（頁面路由 + 元件拆分）重新設計，不要照抄
prototype 的 tab-content + 全域函式寫法，也不要照抄它的假資料與簡化邏輯
（見 spec.md 裡已補充的錯誤處理、loading 狀態等真實需求）。

【資料模型規劃重點】
請規劃以下幾張核心資料表（實際欄位與正規化方式由你決定，這裡只列出
語意上需要涵蓋的資訊）：
- 使用者基本資料：LINE 使用者識別碼、年齡、身高、體重、活動量等級、
  計算出的 BMR/TDEE
- 飲食紀錄：使用者 ID、拍攝時間、原始照片（或照片路徑）、辨識出的食物
  項目列表（名稱、預設份量、使用者調整後份量、熱量、蛋白質、碳水、脂肪）
- 通用食物營養對照表：食物名稱、每 100g 熱量與三大營養素

【重要】此通用食物營養對照表未來會與「推薦餐廳」模組（第二輪）的店家
餐點資料表完全分開，本輪請勿把兩者設計成同一張表或有外鍵關聯，兩者是
獨立資料。

【AI 辨識服務串接的技術決策】
辨識服務與主程式部署在同一台伺服器，屬於內部服務呼叫，本輪先以「同步
HTTP 呼叫、等待回應」的方式設計 API 串接（呼叫 → 等待結果 → 回傳前端），
但請在 plan.md 中明確標註這是待確認的技術假設（open question），未來若
改為非同步（輪詢或 WebSocket）時，目前的 API 設計是否容易調整，也請一併
評估並記錄。

錯誤處理需涵蓋：
- 已知格式：{"items": [], "message": "沒有偵測到食物，請換一張再試試"}
  → 對應前端引導畫面
- 未列在模型資料裡、但實際上線可能發生的：網路逾時、伺服器錯誤（5xx）、
  照片格式不支援等，請補上對應的錯誤處理策略與前端呈現方式

【非功能性需求】
- 拍照辨識過程需要 Loading 狀態的畫面設計
- 份量調整為即時互動（滑桿或輸入框），調整當下前端需即時重新計算並更新
  畫面上的熱量與營養素數值，不需要重新呼叫後端 API（因為換算公式簡單，
  可在前端直接用「每100g數值 × 調整後克數/100」計算）

【本輪不處理，留給後續 plan】
- 推薦餐廳、管理員後台、Flutter 客戶端相關的技術決策不在本輪 plan 範圍
- Rich Menu 分流的技術選型（同一前端不同路由 vs 兩組 LIFF）留到之後決定
