# Caluli 飲食紀錄 LINE Mini App Constitution

## Core Principles

### I. 統一 LINE 登入（NON-NEGOTIABLE）

全系統的身分驗證必須（MUST）統一採用 LINE 快速登入（LINE Login / OAuth 2.0）。禁止
（MUST NOT）開放 Email 帳號密碼自行註冊，亦禁止新增任何與 LINE 並行的自建帳密體系。

四個入口依執行環境採不同串接方式：

- LIFF：由 LIFF SDK 自動帶入使用者身分。
- 一般網頁：走 LINE 官方網頁版 OAuth 流程。
- iOS / Android：走 LINE 原生 SDK；裝置未安裝 LINE App 時必須（MUST）自動退回網頁版
  OAuth，不得（MUST NOT）讓流程中斷。

不論來自哪個入口，後端的權杖驗證與使用者身分解析邏輯必須（MUST）是同一套實作。禁止
（MUST NOT）為特定入口分岔出獨立的驗證路徑或專用端點。

**理由**：登入是所有功能的前置條件，四端分岔會讓驗證漏洞散落在四處且難以一致修補；
單一驗證實作使安全性審查與修正只需進行一次。

### II. 執行環境自我偵測，不假設 LIFF

所有前端服務必須（MUST）具備判斷「目前是否執行於 LIFF 環境」的能力，並依判斷結果分流：
處於 LIFF 環境時呼叫 LIFF 專屬功能，否則導向對應的一般網頁流程。

任何程式碼路徑禁止（MUST NOT）預設一定執行於 LIFF context 內，包含但不限於：直接存取
LIFF SDK 物件而未先檢查、把 LIFF 專屬能力（分享、關閉視窗、取得 LINE profile）當作必然
可用、或在非 LIFF 環境下讓頁面因缺少 LIFF 而白畫面或崩潰。

**理由**：產品同時以 LINE Mini App 與一般瀏覽器為入口，隱含的 LIFF 假設會讓網頁版在
上線後才暴露為不可用。

### III. 單一後端，多客戶端即時呼叫

LIFF、一般網頁、iOS App、Android App 四端必須（MUST）即時呼叫同一組後端 API，並以後端
資料為唯一真實來源（single source of truth）。

客戶端禁止（MUST NOT）在本機保留離線資料作為業務資料來源，亦不得（MUST NOT）為此開發
資料同步、衝突解消或離線佇列機制。客戶端僅可保留必要的登入權杖與暫時性 UI 狀態。

**理由**：四端各自持有本機資料會製造同步與衝突成本，且與本專案的規模與需求不相稱。

### IV. 角色與權限隔離（NON-NEGOTIABLE）

一般使用者與管理員的 API 權限必須（MUST）完全隔開。後端必須（MUST）建立一層僅管理員可
通過的權限檢查層，所有管理端 API 必須（MUST）通過該層才能執行。

僅持有一般使用者登入狀態的請求，對任何管理端 API 都必須（MUST）被拒絕，不得（MUST NOT）
僅靠前端隱藏入口或前端路由保護來達成。權限判斷必須（MUST）在後端完成。

**理由**：前端隱藏不是權限控制；缺少後端強制檢查時，一般使用者的合法登入權杖即可直接
觸及後台功能。

### V. 營養資料表分離

「拍照辨識用之通用食物營養對照表」與「特定店家／餐點之營養值」為兩套完全獨立的資料，
必須（MUST）存放於各自獨立的資料表。禁止（MUST NOT）合併為同一份資料表，亦禁止
（MUST NOT）以型別欄位在單一表內混存兩者。

兩套資料的寫入來源、更新週期與查詢路徑必須（MUST）各自獨立；跨兩者的關聯僅可透過明確的
參照建立，不得（MUST NOT）以隱含約定共用主鍵語意。

**理由**：通用營養對照表是辨識模型的估算基準，店家餐點營養值是特定商家提供的既定數值，
兩者的正確性責任歸屬不同，混存會使錯誤資料互相汙染且無法回溯來源。

### VI. 技術棧約定

本專案的技術棧如下，變更需依 Governance 的修訂程序處理：

- 前端：Next.js（作為 LIFF 容器，同時支援一般瀏覽器）。
- 行動端：Flutter（iOS / Android），以獨立專案維護。
- 後端：FastAPI。
- 資料庫：PostgreSQL。
- AI 辨識：YOLO + Hugging Face（模型選型、版本與推論細節由各輪 spec 定義）。

在既有技術棧可達成需求時，禁止（MUST NOT）為單一功能引入平行的框架、資料庫或執行環境。

**理由**：固定技術棧讓四端與後端的開發、部署與成本估算可預期；AI 細節留待各輪 spec，
是因模型選型會隨辨識準確度驗證結果調整。

### VII. 免責範圍（NON-NEGOTIABLE）

本產品僅提供熱量與營養素的估算參考。禁止（MUST NOT）提供醫療級營養診斷、疾病判讀或
治療建議，亦禁止（MUST NOT）以任何文案、UI 或 AI 產出內容暗示其結果具醫療效力。

所有呈現辨識結果與營養數據的介面必須（MUST）明確傳達其為估算值。

**理由**：辨識與估算存在固有誤差；逾越參考定位會構成醫療宣稱，帶來使用者健康風險與
法遵風險。

## 架構約束

- 後端 API 契約對四端一致：同一功能不得（MUST NOT）因客戶端不同而提供語意不同的端點或
  回應結構。客戶端差異僅允許存在於呈現層與登入串接方式。
- 環境差異的處理必須（MUST）收斂在前端明確的能力偵測層，而非散落於各功能元件內。
- 管理員權限檢查必須（MUST）是可被單獨測試的獨立元件，不得（MUST NOT）在各端點內重複
  手寫判斷邏輯。
- 兩套營養資料表的 schema 與遷移必須（MUST）分別管理，遷移腳本不得（MUST NOT）跨兩者
  混合變更。

## 開發流程與品質門檻

- 每輪 spec 與 plan 必須（MUST）先確認與本憲章各原則相容；發現衝突時，必須（MUST）先
  修改設計或依修訂程序修改憲章，不得（MUST NOT）在實作中默默偏離。
- 涉及登入、權限或營養資料表的變更，必須（MUST）具備對應測試：至少涵蓋「一般使用者
  存取管理端 API 被拒絕」與「非 LIFF 環境可完成登入流程」兩類情境。
- 引入超出既有技術棧的元件時，必須（MUST）在該輪 plan 中書面說明理由與替代方案評估。
- 各輪交付前必須（MUST）確認四個入口的登入路徑皆可運作，包含未安裝 LINE App 的退回路徑。

## Governance

- 本憲章的效力高於其他開發慣例與文件；發生牴觸時以本憲章為準。
- 修訂程序：任何修訂必須（MUST）以文件形式提出，載明變更內容、理由與對既有實作的遷移
  影響，經專案負責人核准後方可生效，並同步更新版本號與修訂日期。
- 版本政策採語意化版本（semantic versioning）：
  - MAJOR：移除或以不相容方式重新定義既有原則、變更治理規則。
  - MINOR：新增原則或章節、實質擴充既有規範。
  - PATCH：釐清用語、修正錯字等不改變語意的調整。
- 合規審查：所有變更審查（PR / review）必須（MUST）確認符合本憲章；標記為
  NON-NEGOTIABLE 的原則不接受例外。其餘原則的偏離必須（MUST）在該輪 plan 中明列理由，
  未載明者視為不合規。
- 執行期開發指引以各輪 spec、plan 與 tasks 文件為準，該等文件不得（MUST NOT）與本憲章
  牴觸。
